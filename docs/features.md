# Pia features

The full tour. For setup, see the [README](../README.md).

**Pia, the assistant.** Pia is the owner's private assistant and the only assistant behavior in the app. The owner can set its display name in Menu → Extensions; its default name is Pia. It uses the normal enabled tools and session-management tools, and it can do small tasks itself or delegate larger tasks to ordinary sessions. It works in `<dataDir>/pia` and reads the shared `<dataDir>/pia/AGENTS.md` from every folder. The app creates that file only when none exists. Closing the panel preserves the conversation. **Start fresh** resets its active context but keeps its history, workspace files, and managed sessions. Subagents and Background tasks are off by default unless the owner enables them. Agent Teams remains available; its compatibility with Pia is untested. Pia uses ordinary session compaction. A summary can include tool results and text from outside. Old `assistantProfile` config values are ignored and removed on the next config save; `assistantName` remains configurable.

**Local tool discovery.** Sessions and Pia start with `read`, `write`, `bash`, `ls`, `tool_search`, and `tool_load`. They also get `rg` when ripgrep is executable on the server's PATH at startup. A compact `available_tools` prompt section lists enabled tools with summaries of at most 5 words. It refreshes before each model request, including after extension reloads; disabled and conversation-excluded tools stay out. The agent can load an exact tool name directly when its purpose is clear. Otherwise, it searches for descriptions first. `edit` and optional tools load on demand. `tool_search` returns names and descriptions (at most 160 characters each); it never loads tools or their guides. Exact names take priority. Search returns at most 3 matches by default (10 maximum). `tool_load` accepts 1 to 10 exact names. Unknown or disabled names reject the whole batch. Only selected schemas and guides appear on the next request. Loaded tools remain in that conversation across restart and compaction. New sessions start small. Optional built-in tool guides appear only after their tools load; approved lessons, safety sections, and unknown extensions' sections stay present. Discovery does not enable disabled extensions or grant permissions. Pia's session-management tools remain offered up front. To roll back tool exposure locally, start the server with `PI_POCKET_TOOL_DISCOVERY=off`. `PI_POCKET_TOOL_DISCOVERY=on` forces it on for testing. This does not remove saved tool-loading choices.

- **Durable runs.** Every model request, tool call, queued message, and subagent is a durable task in one SQLite file. Kill the server mid-run and start it again: the run continues. A tool call that was cut off reruns if it is safe to; otherwise the model is told it was interrupted.
- **One palette, light and dark.** The app has one set of colors, after [Rosé Pine](https://rosepinetheme.com): dark mode is Rosé Pine's own, light mode is after Rosé Pine Dawn, and Love (a soft rose) is the accent in both. Contrast follows Modus Vivendi and Operandi: body text at 7:1 or more on its ground, and every color used as text at 4.5:1 or more. The look is soft tiles: rounded windows and controls on 1px hairlines, soft shadows only on what floats, Geist for words and JetBrains Mono for code, paths, and numbers, with JetBrains Mono's own italic and the Nerd Fonts icons that prompts and tools print (bundled in `web/fonts/`; `web/fonts/SOURCES.md` says where each came from). Menu → **Appearance** has a **Light and dark** section with one switch, **Auto dark mode**, which follows the system's light or dark. With it off, a **Light** or **Dark** choice shows. The launcher finds **Appearance**, **Turn auto dark mode on/off**, and **Use light mode**/**Use dark mode**; `/theme auto`, `/theme light`, and `/theme dark` do the same, and `/theme` alone opens Appearance. The new mode grows as a circle from where you tapped.
- **Sheets and controls.** Sheets have a 56px title bar on wide screens, a back chevron when opened from another sheet, grouped inset lists, round toggles, and segmented settings. On phones they keep their bottom-sheet grip and drag-to-close gesture. Text sheets have Cancel and the main action together at the bottom; all existing keyboard and back flows stay available. Buttons, fields, and search share the same rounded controls across the app.
- **Tiled windows and motion.** On wide screens the sidebar and the session are Hyprland windows, softened: 8px gaps, rounded corners on a hairline, and a soft accent ring on the one under the mouse. Motion uses Omarchy's Hyprland curves: windows pop in at 87%, sheets and popovers rise a little as they fade in, and leave quickly, new messages slide in, and notices count down until they go. While the agent works, the conversation shows what it does; elsewhere a working session's square steps around and a small dot pulses (both hold still with reduced motion). Appearance can turn tiling off (no gaps, square corners, no ring), reduce motion (or follow the system's setting), choose Fluid motion (sheets, menus, the launcher, and notices arrive on a spring and leave quickly, over a frosted scrim; what they hold, and a tool group's first steps, follow a step apart; a message sent lifts off from the message box; each new paragraph of the agent's answer fades in, and its caret breathes; a pressed button springs back; and folding the sidebar morphs the windows into place; Width and tiling change at once, as they are set from a sheet or the launcher, which morphs skip; Auto never picks it), change the conversation's text size (13, 15, 17, or 20, or any size from 10 to 32 px typed in, in half pixels), set the width (Comfortable, which grows with a wide window, Wide, or Full: how much of the window the conversation and the message box take, per browser; phones stay as they are; a reply's code block with long lines grows past the column, centered on it, where plain text and Markdown wrap in the column, and a wide table grows toward the window's edge), set the density (Comfortable, Compact, or Tight: less room between turns, inside message cards and activity groups, between the conversation's lines, in the session list's rows, around the message box and the status line, in sheets and their lists, and in the top bar, while font sizes stay and rows on a touch screen stay a thumb tall), show the agent's thinking while it works, and show the reply speed under the message box.
- **The sidebar.** A rail and the session list beside it. The rail holds the agent (which goes to the home screen), Sessions (which folds the sidebar to numbered sessions and unfolds it again, as Ctrl/⌘+B does), the tools (Pia; Quick notes; Links, for the owner, to HTTP services on the local network or tailnet; Running now, with how many sessions work; extensions' buttons; Providers, for the owner; a light/dark switch), and you. Peek tiles, the subagents board, and People open from the launcher (Ctrl/⌘+K) and the menu. The open sidebar is 240 px wide by default (the rail and a 184 px list); a browser that kept the old 312 px default moves to 240 px. The list has Recent, Folders, and Archived in a segmented switch; sessions grouped by day or by folder, in groups that fold; and pinned sessions on top (per browser). Each session is one line: a square in its folder's color whose shape says where the session is (stepping quadrants while the agent or its subagents work, two bars while a call waits for you, a cross when its run failed, solid when it finished since this browser last had it open or is marked unread, and hollow once read or never run), its title (semibold when marked unread, or when open, and the open one on the accent's soft fill), and on the right a small pill with ⑂ and how many subagents work there (or failed with nobody dealing with it yet, in red), who else is there, a pulsing dot while the agent works or a "needs you" pill while a call waits for you, a dot for a session this browser marked unread, and how long ago; its folder and model are in its tooltip. Hover a row to archive, pin, or mark it unread; on a touch screen, hold a finger on it (the row shows the press, and moving the finger scrolls instead) for a sheet that pins it, marks it unread or read, archives or unarchives it, or selects it. Marks are per browser, like pins (a session's square counts as read here when this browser opens it, or has it open in sight as its run ends; a failed run's cross stays until its next run starts, and a restart forgets it), and opening the session clears its mark; the session's menu marks the open one unread and goes back to the list. A session that another one started (Agent Teams) shows under it, with a branch line to it, as deep as they go (up to three steps of indent, so a phone's list keeps its room), and the numbers (Alt+1…9, the folded rail) follow the tree; a pinned one stays among the pins, and in Folders one in another folder stays in that folder's group. A session with linked sessions under it has a pill on its right with how many and a chevron: a tap folds them away under it, and again shows them; a fold holds in that browser across reloads, a folded row shows a dot when one under it waits for you or failed, and a search shows every match, folded or not. Someone who cannot see the session that started one sees it as a session of its own. A session moves up the list when it is renamed, gets a message, or the agent starts work there for any other reason (a scheduled message, a subagent's report, a message sent again after a restart), so the one that ran last is on top. Archiving says so in a notice that undoes it. Ctrl/⌘+click selects sessions, Ctrl/⌘+drag selects every row it passes (the list scrolls at its edges), and Shift+click selects a run; on a touch screen, after **Select**, taps select more rows or let them go. A bar under the list archives, unarchives, or pins them, and Esc (or back, after Select) lets go. Archiving does not move a session in the list, so one brought back returns to where it was. Drag its edge to resize the list (to 40% of the screen at most), or fold the sidebar to the rail with numbered sessions, like Waybar's workspaces. A rail with more buttons than room (a short window, many extensions' buttons) scrolls as a whole, and its numbered sessions on their own, up to a third of the window; each fades the edge where more is. On phones the drawer and the list with no session open have the same rail. On wide screens with no session open, the home screen shows a fastfetch-style summary, buttons for a new session, the launcher, and Appearance, and the sessions to jump back into.
- **Your own layout.** Appearance → **Top bar buttons**, **Status line items**, **Places**, **Message box buttons**, and **Under the agent's answers** list what shows in each place, the app's own and extensions' alike: a switch shows or hides each one, arrows move it, and **Reset** goes back to the defaults. The menu, More under an answer, Lancet Guard, and the connection's warning always show. Saved in each browser, so a phone and a desktop can differ. - **Links.** The owner's Links button on the left rail, or Links in the launcher, opens tiles for HTTP services on this machine. Tailscale Serve links come first, with the MagicDNS name and HTTPS scheme that preserve TLS. Each tile shows the service title and exposed port. Tailnet and local-network links open in a new tab, so Pia stays open. Loopback-only services that Tailscale Serve does not expose open in Pia Browser when a session is open and Browser is enabled. Refresh scans again. The scan uses Tailscale Serve status and Linux's listener list.
- **Peek tiles.** Off until you turn them on: the menu's **Peeks** tile, Alt+P, `/peek`, the launcher, or Appearance switches them on or off in one step, and so do the rail's **Peek tiles** button and the tiles button in the top bar, which shows wherever its pane is 480px wide or more (while off, it has a dot when another session waits for you). Then other sessions' live work shows beside the one you are in: one tile per session that is working, waiting for an approval, has subagents at work, finished since this browser last had it open, or is pinned, plus the one you just left. Each is a card with the session's folder square, title, and path, its last three lines (what was asked, what the agent said, its tool calls and how they went, each in two lines at most, with a mark for who or what said it), the subagents at work there, and a footer with its state in words; it changes at most once a second, and only its square moves while the session works. Its subagents at work get a line each: the state square, the name, and what it does this moment (the call it runs, the one it waits to allow, or its words), from its own peek; a tap opens it. Those waiting for an approval come first, and a tile shows three at most (the strip one), so it stays a glance however many work: **N more** opens the subagents board at the first one left out. A subagent's call waiting on its session's tile says which subagent asks, and in the column the footer says when only subagents keep the session working or waiting ("3 subagents working"). Click a tile to open its session; the one you leave takes its place, so the tiles stay put. Allow or deny a waiting call right on its tile, which shows the whole command and why the guard asks; a command that does not show whole offers Open instead of Allow, which goes to the conversation it waits in. The ✓ on a finished one marks it seen. On wide screens the tiles are a column that slides in where the Browser panel docks when it is not open, with **▲/▼ N need you** at its edge for waiting tiles out of view; narrower screens (and wide ones with a panel open) get a strip under the top bar that swipes sideways. Only the tiles on screen are live: once scrolling settles, the tab tells the server which, and the rest keep their last lines (their marks stay current from the session list); a tab in the background keeps none live, and with tiles off nothing is sent at all. Peeking is not being there: it does not show you in the session's people.
- **Launcher.** Ctrl/⌘+K (on a touch screen, the **Launcher** tile among the places, or the ⌘ button in the session search) opens a rounded search window for sessions and actions, with fuzzy matching. Search-type pills sit above grouped results with folder-color tiles, or action icons; the selected row has a soft fill. **All**, **Sessions**, and **Actions** select the search type without clearing your words; `>` and `@` still work. All starts with six recent sessions; **Show all** searches the whole session list, including archived sessions. Result counts show when a list is capped. Titles and folder or command details highlight matches, and sessions show their current, working, waiting, or archived state in a pill on the right. Arrows, Tab/Shift+Tab, and PageUp/PageDown move the selection; Enter opens it. **Close**, Escape, a tap outside, or Back closes the launcher. Each opening starts with a fresh search and a focused input, even when it reopens during its fade-out. On a phone it is a sheet from the bottom edge, like the app's other sheets: drag it down to close it. On a touch screen it opens without the keyboard, so the results stay in sight; a tap on its search brings the keyboard up.

Type `memory` to find **Memory**, or type `Instructions` or `AGENTS.md` to find the instruction editor. Type `>` before a command to search commands only. Select a result to open it.

Three columns of rounded place tiles open the core places: Files, Changes, Browser, Find, and Branch when available; badges show counts, and open places are tinted. Extensions' panels keep their own top bar buttons, and Links, Artifacts, Pia, and Peeks open from the rail or the launcher. Take turns is in neither. Project trust, Instructions for the agent, and Working directory are in the App group. Extensions sits above the App group. Rows have right-aligned hints. App includes **Memory** (the lessons database path and editor), **Instructions (AGENTS.md)** (each loaded file path and editor), and **Keyboard shortcuts** (`?`). Arrows, Home/End, and Tab move through the controls; Esc, Back, Close, or a tap outside closes the menu. Back from a sheet it opened returns to the menu.
- **Keyboard.** Alt+1…9 jumps to a session (hold Alt to see the numbers), Alt+↑/↓ goes to the previous or next one, Alt+N starts a new one (where Ctrl/⌘+1…9 starts it in a favorite folder), Alt+B opens or closes the browser, Alt+E the Files tile, Alt+T turns Show thinking on or off, Alt+V starts or stops dictation, and `?` lists every shortcut. On a computer, a session opens with the caret in its message box, ready to type; on a touch screen it waits for a tap, so the keyboard does not cover the conversation, and on a Mac a session opened with Alt+1…9 or Alt+↑/↓ leaves the box alone, so the next Alt shortcut still works (Option types characters in a box).
- **The conversation.** A column of turns, made for phones. Your messages are cards with the sender's avatar (the accent for yours, the sender's color for someone else's), who sent each and when; the agent's replies are plain prose at Appearance's text size, streamed as they come (lists keep a quiet marker column; code, tables, and rich blocks are rounded cards). The **Message time** item under completed replies shows the time, with the date for earlier days, and can be hidden or moved in Appearance → Layout. What the agent does between its words, its thinking and tool calls, folds into one line that says what it did and for how long ("Thought, searched, read 2 files, ran 1 command · 18s"), and opens, as a card, into a timeline: a line per call with a circle for how it went (✓ done, × failed or denied, ! waiting for an approval, a spinner while it runs, ⑂ for a subagent, ✦ for a thought) and what it came to (lines added and removed, lines read, matches, tests passed, an exit code, "needs approval"), and tapped, its input and output, with the diff viewer's diffs for edits (line numbers, syntax colors, and the words that changed) and bash's live output. The newest turn's groups are open and earlier ones closed, unless Appearance's **Keep activity folded** (off by default) keeps them on their line until you open one; a thought alone still follows Show thinking. An approval is a card at the end of its turn (the command, the reason, Deny and Allow; once answered, the call's line says who allowed or denied it), and while the agent works one line, a pulsing dot with the state in the accent (the warning color while it waits for an approval), says what it does (thinking, working, waiting for an approval, retrying) and for how long. With **Show thinking** on in Appearance (or Alt+T, or the launcher), the current thought shows above that line as it streams, and the thoughts in the conversation show their words once written (a thought alone in its group opens, and one on a timeline opens its step). A chevron before the line's dot folds the live thought away, and again brings it back. Alt+T shows a short on/off notice, even while the agent is idle. During tool calls the latest thought stays; a new response clears it until the model shares new thinking. Models that share none say so, rather than showing an old thought as current. A fold holds in that session, also over a reload, until you open it again; the setting is off until you turn it on, in each browser, and while it is off or folded the live thought is neither selected nor drawn. The reading area follows new words until you scroll up in it, and follows again for each new thought. While the agent works, **Steer**, **Queue**, or **Interrupt** beside the model chip says whether a message steers the run, waits for it to end, or stops the run at once (the tool call too, as Stop does, which also withdraws what waits in the queue) and is sent after; Interrupt goes back to Steer after one use, or when the agent stops before it was used, while Steer and Queue stay as chosen; queued messages can be withdrawn, and your own, tapped open, can move to Queue or Steer until the agent reads it, or go now as an Interrupt (a second tap confirms; `CONFIRM_INTERRUPT` in `web/composer.js` turns that off): that stops the run and sends only that message, while every other queued message, from everyone, stays queued in its order with its sender and mode (a restart in between loses or repeats none), and so do subagents' reports; with take turns on, moving one to Steer or Interrupt waits for your turn at the wheel, as sending does; Stop (or Esc twice) stops the run. A run stopped in the middle of a tool call ends with a "Stopped." line under its card.
- **Getting around on a phone, with one hand.** Back (the swipe, Android's back button, the browser's) goes back to where you were: it closes what opened last (a sheet, the menu's next sheet back to the menu, a file back to the Files tree, back to Changes when the file was opened from there, the Files tile or the Browser panel, the drawer) before it leaves the session, and leaving goes to the session before or to the list, scrolled and searched as you left it. A session opened straight away (a link, a notification) has the list under it, so back does not leave the app. What you use most is a thumb's reach from the bottom edge: the button beside the message box (or a swipe up from it) opens the places, a short sheet of big tiles (Files, Changes, Browser, Find, Branch) with a compact icon below them that opens the session menu. On the conversation, swipe left for Files and right to go back; in Files, swipe right to go back. Each swipe shows a mark that lights when letting go will act. The top bar leads back to the list (counting other sessions that wait for an approval) and keeps only the buttons with something to say. Every control is a thumb's size on a touch screen (small ones, such as a code block's Copy or a reply's Pin, keep their look and take a wider tap); a tap anywhere on the message box, off its one line of text, still goes to the text; a quick second tap does not land on whatever just slid in under it; tables in replies scroll sideways instead of crushing their columns; a diff's header keeps the file's name on a line of its own on a phone; and the command a peek tile asks about opens its session when tapped. The Files tile and the browser slide in as screens of their own and slide away on back, a file slides in over the tree, and the browser's tools sit on their own row under the address. Drag a sheet down, or the drawer left, to close it. In an iPhone home screen app, which has no back gesture of its own, swipe in from the left edge to go back.
- **Forks.** Tap the agent's reply → More → **Fork from here**: a new session with everything up to that reply, which then goes its own way. Tap one of your messages to **edit it and send it again**, or send any message again, to the same model or another one (a retry). Each makes a new session that forks just before the message; the original stays as it is. A fork gets its own chat (with the pins of what it inherited), a link back to where it came from, and optionally a git worktree of its own.
- **A new context.** Menu → **New context** (or `/reset [note]`): the agent starts fresh and no longer sees the messages so far, while everyone still does. An optional handoff note carries over what matters.
- **Instructions for the agent.** Menu → **Instructions for the agent** (or `/instructions …`): ground rules the agent gets with every message in this session, such as "use pnpm, not npm". Everyone in the session can see them.
- **Instruction files.** Menu → App → **Instructions (AGENTS.md)** shows the global context file under the agent directory and the context files the agent loads from current session folders and their parents. It also shows Pia's shared `<dataDir>/pia/AGENTS.md` when Pia is active. Each row shows its full path; the owner can edit and save each file to disk. New instruction text applies on the agent's next request, within 30 seconds. The agent's context-file names and precedence follow its `configuration.md`.
- **Compaction review model.** In Menu → **Extensions** → **Installed**, the owner can choose a model and thinking level to review and write summaries. It applies to automatic and manual compaction, and does not change the session's model. Leave it unset to use the owner's default model, or each conversation's model when no owner default exists. For one manual compaction, choose another model in the Compact sheet or run `/compact --model provider/modelId [what to keep]`; that choice overrides the default only for that request. The summary model's usage counts toward the conversation and its payer. Pia uses ordinary session compaction and this setting.
- **Memory.** Short lessons the agent keeps across sessions: how to build and test a project, a gotcha it hit, a convention, a preference someone stated. The agent proposes one with its `memory` tool (one or two sentences each, never secrets) only when a person asks for it, or when the agent is sure that it will help in many later sessions, never for a one-off detail, and proposes fixing or forgetting one that turns out wrong; the owner approves. What the agent reads (a web page, a post, a comment, a file) could talk it into a "lesson" that would reach every later session, so nothing the agent saves, changes, or forgets counts until the owner says: **Approve** and **Discard** show right under the agent's memory call, with the words that wait and where they would apply (this project, or everywhere: every session and Pia), and in the sheet. Approve approves only what you saw: if the agent changed it since, the app says so and shows the new words. Lessons and project names are kept on one line, without invisible characters, so the agent reads only what the owner saw. A change or forgetting the agent proposes leaves the lesson as it was until then. Lessons you add yourself count at once. Each is for this project or for everywhere: a project's lessons reach every later session in the same repository, its worktrees included (or the same folder, outside a repository), and everywhere's reach every session and Pia. Menu → **Memory** (its hint says how many apply here and everywhere) lists them in those two groups, each with who saved it and a link to the session it came from (when you may see it), with Edit and Forget; type one in to add it by hand, for this project or everywhere, or use `/remember run the tests with make check` or **Remember…** on a message. A guest's lessons wait for the owner too, and a guest's change to one in force is a proposal they can withdraw. What waits shows at the top of the owner's sheet; the menu's hint says how many. Lessons waiting take no room from the approved ones, and a person (or the agent for them) may have 20 waiting at most. Only the owner, or whoever saved a lesson, changes or forgets it; viewers only read. A project keeps 40 lessons and everywhere 30; past that, forget one first. Changes show as lines in the chat. Turn it off in Extensions. The App menu's **Memory** entry shows the storage path, `<dataDir>/pocket.sqlite`, and opens the lesson editor for a chosen session. Lessons are durable database records, not a text file; the app writes changes to disk.
- **Plan mode.** The **Plan** chip by the message box (or `/plan`): the agent reads files, runs read-only commands, and uses tools their extensions mark read-only, then proposes a plan; writing, editing, and other commands are blocked. Subagents inherit plan mode and explore under the same restrictions. **Approve plan** turns plan mode off and tells the agent to go ahead; it waits until the agent has answered since plan mode went on.
- **Scheduled messages.** `/schedule in 2h check the deploy`, `/schedule tomorrow 9am …`, or `/schedule every weekday 8:00 summarize CI`, or Menu → **Scheduled messages**: the agent gets the message at its time, in this device's time zone, even with nobody watching, and the people in the session get the usual "the agent finished" notification. The agent can schedule its own follow-ups with its `schedule` tool. Each schedule is a durable task: a restart while it waits keeps waiting, one after its time sends at once, and none is ever sent twice. A schedule is cancelled, with a line in the chat saying why, once its person can no longer steer the session or a spend limit is reached. Limits (settable since 0.24.0): a session holds 50 schedules, a message 4000 characters, a repeat comes at most every 10 minutes (a short repeat can cost money in model calls), and `in …` reaches 366 days ahead. The owner changes each in Menu → Extensions, under Scheduled messages; a change applies at once, to new schedules only.
- **Done when.** `/until npm test`: after each of the agent's answers, the check runs in the session's folder; while it fails, the agent gets the end of its output and keeps going, for five checks at most. A bar above the message box shows how it stands. With Lancet Guard on, the check must be a command the guard allows outright. In plan mode the check waits until the plan is approved, and past a spend limit the agent stops going on. A check cut off by a server restart is not run again, as it may have done part of its work: the agent hears so, and its next answer is checked.
- **Mention files.** Type `@` in the message box to pick a file or folder from the session's folder: `@` alone lists its top, `@src/` a folder's own files, and anything else matches across the whole folder (`@srvapp` finds `src/server/app.ts`). Tab or Enter (or a tap) puts the path in, and a folder opens to its files. The agent gets the message as written, `@src/server/app.ts` and all, and reads what it names; or tap **Send them along** above the box to send the files' contents with the message, as Claude Code does (text files up to 100 KB each, images as images when the model takes them). The list is git's in a repository (so ignored files stay out), and a walk that skips hidden and dependency folders elsewhere; your browser fetches it once and matches as you type, so suggestions never wait on the network.
- **Shell commands.** `!git status` runs in the session's folder, and the agent sees the command and what it printed with your next message, as in the agent's terminal app; `!!git status` shows it only to the people here. While it runs, a row says so, with Stop (it is in Running now too). A restart while it runs does not run it again: its entry says it was cut off. With Lancet Guard on, a command from anyone but the owner must be one the guard allows outright. A command the agent sees counts as its person's message: the agent works for them from there, as for a steer. These are a person's own commands, not the agent's: plan mode does not hold them back. Stop one from its row, or from Running now on any device.
- **Background tasks.** Since 0.24.0, the agent's `background` tool starts a command without waiting for it: a dev server, a watcher, a long build or test run. It runs in the session's folder, reads what the command printed since it last looked (the last 20,000 characters at most), lists the session's tasks and how they ended, and stops one: every process it started, politely, then by force after 4 seconds. A task runs while any process of its group runs, so a command that starts a server in the background and exits keeps its task running. A daemon that leaves the group (a build tool's) does not keep it running: the task ends, says which processes it left, and a stop ends them too. When a task ends by itself, the agent gets a message that starts with `[background]`, with its exit code and the end of its output, as data; the agent can start one without it. In the conversation, that message shows as a card: the task's id, how it ended and how long it took, its command, and the last 8 lines of its output as printed, with the rest behind **Show all** (a person who types `[background]` themselves keeps their message as theirs). Each command runs detached from the server, with its output in a log in the data folder (`background/`, in 4 MB segments), so it goes on across a restart from the app; stopping the whole service (systemd) ends it. A durable task watches each one, and after a restart finds the same processes again by their pid, start time, and a marker in their environment. A start is reserved before its process starts, so a tool call run again after a crash never starts the command twice: the watch adopts the processes it finds by their marker; with none left, it tells the agent the exit code the command left, or that how it went cannot be known. A start passes Lancet Guard as a bash command does, and plan mode blocks it (listing, reading, and stopping stay allowed). Each task shows in Running now, where anyone who may steer the session can stop it. While any runs, the session's status line shows **N in background** (a tap opens Running now), its row in the session list shows a terminal mark with the count, and the rail's Running now button counts the session (since 0.25.0). Limits: 10 running at once in a session (the owner changes it in Menu → Extensions, under Background tasks); a log past 50 MB loses its oldest segments, whole, and a command that writes more than 200 MB in a quarter of a second, or more than 500 MB in 10 seconds, is stopped at once, and the agent is told why; the last 20 ended tasks of a session stay readable. Sessions only: not subagents or Pia. Linux only (it follows processes through `/proc`); it needs bash and `split`.

- **Webhooks.** Menu → **Webhooks and watches**: an address that other services (GitHub, a deploy, a monitor) post to, each post becoming a message to the agent in a session, or to Pia, as the work of whoever made the hook: their instructions first ("When a deploy fails, find out why and fix it"), then what was posted, trimmed of noise such as API addresses, and fenced as data. A GitHub hook is signed: GitHub gets the address and, separately, a secret (its Payload URL and Secret), and a post gets in only with GitHub's signature made with it, so whoever sees the address (the repository's admins do, in its settings) cannot post as the hook. Unless a GitHub hook is made **From anyone**, what people outside the repository wrote does not reach the agent (the repository's people are its owner, and the organization members and collaborators whom GitHub says can write to it, asked through `gh`, which must be signed in to the host and able to push there, or else only the owner counts; bots count on pull requests and what is said on them, never on issues): a post an outsider started (their issue, comment, pull request, review, or discussion) is dropped with a 202 that says so; in a post the repository's people started, the body of anything an outsider wrote in it (the issue under a member's comment, a review thread's comments) is left out, its title kept; a workflow run goes only when a branch of the repository itself started it (a push, a schedule, a manual or API dispatch, or another workflow), so one a pull request (a fork's too), an issue, or a comment started is dropped, and so is one whose head repository GitHub does not show; workflow jobs, check suites, and check runs do not say where their run came from, so they are dropped too, as are a commit status on no branch of the repository (a fork's commit) and a security advisory someone reported; and pushes, releases, and other posts that name no author go as they came. Services must be able to reach the server: through a tunnel, a public address works for GitHub. - **Artifacts.** The `artifact` tool publishes versioned HTML pages, Markdown documents (shown in the app's colors), or SVG images. Give it `content`, `edits` against the latest version, or a `path` to a UTF-8 text file on the server (up to 2 MB). A path can be absolute, start with `~/`, or be relative to the session's folder. The file is copied into a durable version, not linked: changing or deleting the source does not change the artifact. For a new artifact, `.html`, `.md`/`.markdown`, and `.svg` infer its type; a path update keeps the existing id's type. A page can carry a bundle of files (since 0.26.0). `assets` adds up to 200 entries, each `{ name, path }` (a file on the server, binary allowed, copied and not linked) or `{ name, content }` (UTF-8 text): images, fonts, stylesheets, scripts, data files, or more HTML pages. A name is a relative path of letters, digits, dots, underscores, and hyphens, up to 200 characters, with no `.` or `..` segment. A new version keeps the assets of the one before it; an entry with the same name replaces one, and `removeAssets` drops some. One asset is up to 5 MB, and one version's assets up to 20 MB. A relative URL in the page (`assets/logo.png`, `about.html`) loads from the bundle in the viewer, in an inline card after Run, in the artifact's own tab, and in a published link. Each file is sent with the sandbox's policy, `nosniff`, and a type from its extension (an unknown one is never HTML). Assets are stored once for each content hash. A private page reaches its assets through a signed address that lasts 12 hours, so a page left open longer loads new assets only after a reload. `group` (a lowercase slug) puts artifacts together as variations of one design, and `kind` (`page` or `deck`) says what a design is; Design uses both. Artifacts from before 0.26.0 work as they did. The `artifact_inline` tool is the same store for HTML only (`content` or `edits`, no path): its call shows as a card in the reply, between the agent's words, instead of a link (see Rich replies). The agent's guide says when to use which: the card for a small interactive piece that belongs to what it is explaining, the viewer for a whole page, a game, a Markdown document, or an SVG image. An id made by either tool takes versions from both, but `artifact_inline` refuses an id that is Markdown or SVG, and the `artifact` tool cannot change the type of an id that has had an inline version (a card names a version, and the page comes by the artifact's type): the agent uses a new id for that. The agent's guide mentions `artifact_inline` only in sessions that have the tool, and says that only a direct call shows a card. The Artifacts sheet lists every version in a rounded card grid; opening one shows the sandboxed viewer (or its own tab). The list does not run artifacts as previews. Artifacts cannot reach the app or its cookies. In the viewer, an HTML artifact can ask for two things, which the agent knows how to build: a **follow-up**, a message it puts in your message box (after your draft, starting with which artifact it is from, with any selection as JSON) for you to read and send, never sent by itself, and only after you tap the page (a real tap or key press in the page, up to 5 seconds before: the page cannot fake one, and `window.focus()` does not count; each tap serves one follow-up), at most every 2 seconds (the viewer then closes, so the box shows); and **saved state**, up to 16 KB of JSON that it saves for you alone, so its filters and inputs come back after a reload, a restart, or on another device. Saved state stays out of the agent's context, belongs to the artifact rather than a version, and starts empty in a fork; a page that changes the state's shape names a new schema, and the old state then reads as none. Only people who can write to the agent get a follow-up; a viewer gets a notice. HTML run from a reply (▶ Run) can offer a follow-up too, but keeps no state. Only the artifact's first page is heard: as it starts, it opens a private channel to the app (a script the server puts first in an HTML artifact's page when a frame asks for it, and in the frame page that runs a reply's HTML), and everything goes over that channel, so a page the frame goes on to cannot use it and an answer still on its way never reaches it. `schema` is a string (a number is refused, for a get and a set alike). The bridge is for HTML artifacts, not Markdown or SVG. Neither works in a published link or an artifact's own tab. A session keeps up to 300 saved values; a person removed from the app keeps theirs until the session goes. **Share** in the viewer publishes one artifact to anyone with the link (`/pub/<token>`), with no sign-in: the page is the artifact's own sandboxed one, so it still cannot reach the app, and its address is the whole of the access. A bundle's files are at `/pub/<token>/<name>`, checked on every request: ending or expiring the link closes every file, a link that follows the newest version follows its assets, and a pinned link keeps its own. A published page gets no bridge. A share either stays at the version it was made from or follows the artifact's newest, and either lasts until it is ended or closes after a day, a week, or a month; **End** closes it at once, and the address then answers nothing. Only people who steer and see every session publish or end one, or see its address, never viewers or someone invited to a single session. The sheet lists the session's links still in force, with the address to copy; it starts at the server's public address when a tunnel gives one, else at this browser's.

- **Waiting out provider limits.** When a provider's limit stops a run (a 429 or an overload, a Claude or ChatGPT usage window, a model's cap), Pia waits for it to clear and goes on by itself, instead of failing. It waits until the reset time the provider gave (or, with none, tries again at growing intervals), then sends one request to find out; if that gets an answer, the sessions waiting on the same limit go on, one at a time. The live line says what the agent waits for, when it tries next, and when the limit resets, with **Retry now**; **Stop** or **Interrupt** end the wait at once, and a message you send meanwhile waits in the queue as always. The session's square is a hollow square with a dot, also on peek tiles, and a subagent's row says it waits. One push goes out when a wait of ten minutes or more begins (Menu → **Notifications** → **Waiting for a limit**). It survives a restart. The owner sets the longest wait (**Wait for a limit** in the Providers sheet: Off, 1, 6, 12, or 24 hours; default 6): what waits is any reset time within that longest wait, load with no time given (an ordinary 429 or an overload), which is tried again at growing intervals for up to 30 minutes, and, since 0.24.0, a plan's usage limit with no time given (OpenAI subscription sharing, Z.ai, MiniMax, OpenCode Go), which is tried again about every 15 minutes, up to the longest wait, counted from the first failure across restarts. What fails the run at once, with the reset in the message where there is one: a window of days (Claude's 7-day window, a Codex window of over 300 minutes), a reset after the longest wait, a usage limit that names a window of days (daily, weekly, monthly), with or without a reset time, and a sign-in that expired or billing. Retry now sends one try each 30 seconds. It never picks another model. Since 0.21.0.
- **Prompt cache keeper.** On by default; `PI_POCKET_CACHE_KEEPER=off` turns it off. While a run waits on a tool call, Pia replays the last request that ended in a tool call, with `maxTokens` 1, at 90% of the cache's lifetime or 10 seconds early, whichever is sooner. It does so only when the expected savings are more than the cost. It keeps the 5-minute cache only: no idle warming, no 1h cache, no request with `cacheRetention` none, and no Anthropic thinking set by a token budget. It stops on a real cached request, when the run ends (Pia's too), on an error, at shutdown, or after 30 minutes. A warm request does not wait for a provider limit. Its usage counts in `pi.usage` and in the spend of the person and session that were paying when it started, and spend limits are checked before each warm. A restart drops the warm timers and does not replay warm requests.
- **Background subagents.** The `subagent` tool spawns named subagents that work in their own conversations while you keep talking. This queue is private to the owner. Other people cannot use it to approve lessons or reach another project's memory.
- **Returning from a subagent.** A subagent's conversation has **Back to main session** above the message box, for viewers too, so the way back stays in sight however long the conversation is. The top bar says which session it is a subagent of.
- **Subagents bar.** Above the message box while a subagent works or has a report on its way: a dot per subagent, how many work and how many are done, and what the newest one does now. Tap it (or the count in the top bar while one works) for a row each: what it was asked, what it does this moment (the call it runs, or what it writes), for how long, whether its report is on its way, **Stop**, and a tap to open it; a call waiting for approval says so, and a failed one says why, and "dismissed" once someone dealt with it (see Subagents board). Done, stopped, and failed ones are counted apart, failed ones first. Once none works it stays until you put it away (×), and comes back, counting only the new ones, when one starts again. Viewers see it too, without Stop.
- **Subagents board.** The rail's ⑂ shows every subagent in every session in the conversation's place: a soft state-colored square each, in a rounded row per session, those that need you first, and under each row a sub-tile for every subagent at work there, with its state and what it does this moment, so a glance says what each is doing without opening one (a tap picks it for the detail card, staying on the board; a double click, or double tap, opens it). A row shows six sub-tiles (three on a phone), and the selected one wherever it is; **Show N more** shows the rest. Working squares pulse; the selected square has a ring, and filtered-out squares fade. A proportional state bar and filter pills with counts say how many wait for an approval, failed, work, were stopped, or are done, and let you filter by one; a search finds a subagent by its name, what it was asked, what it does now, or why it failed. **Needs you** lists those waiting for an approval and those that failed with nobody dealing with it yet. The selected subagent's detail card shows its session, how long it has worked (or when it ended), what it was asked and does now, and its error, with **Open** (**Review the approval** while it waits), **Stop**, and, for a failure, **Dismiss** (off while it is asked; when the subagent failed again since, a notice says so and the newer failure stays). A failure is dealt with once someone who can steer dismisses it, or opens the subagent from the board, its row in the subagents bar, its report or the tool call that started it, or the session menu: it stays on the board as failed ("Failed · dismissed", without the "!"), and leaves Needs you, the rail's red mark, and the session's red ⑂, for everyone, after a reload or a restart too. A message someone sends it, like later work from the agent, settles it by what it comes to, after a restart too: answered, the subagent is done; failing again, it needs someone again. The session's activity says who dealt with a failure, whichever way. Hover a square to see what it does in the line under them; the arrows move the focus between squares and Enter opens the one focused; Esc, back, or × closes it, and on a phone a swipe right does too. Archived sessions show only while a subagent works there. A session keeps its 24 newest finished squares (done, stopped, or failed and dealt with); older ones are counted, as **+N** after its squares and in the bar's numbers. On a phone it is one column, Needs you first, with bigger squares and a bar at the bottom for the one selected.
- **The queue and the bars above the message box.** Messages waiting for the agent show above the message box, with how many wait whenever not all of them show. With the bars there (the subagents bar, plan mode, a goal, a PR watch, a trust question, who drives), they take less than half of the room they share with the conversation when the bars fit in it, and the conversation keeps the rest, staying where you were reading. The bars always show whole; the queue and the subagents' list take what the bars leave, and scroll. Unfolding the subagents bar gives the list the room, one whole row at least: the queue shows fewer rows, or folds to how many wait. With several bars on a short screen, the plan, goal, watch, and trust bars keep one line each, their words cut short and their buttons whole. When even that does not fit (a phone on its side with every bar up), the stack scrolls, and the conversation keeps a quarter of the room, or a few lines, whichever is less.
- **Live editing.** No build step. Edit a file in `web/` and every open browser reloads. Edit a file in `src/server/extensions/` and it is reinstalled into the running server (a running tool call finishes on the old code). For core server changes, use **Restart server** in the menu: running work resumes after the restart. Its sheet says whether a restart is needed (the server files changed since the start, with a dot on the menu button), shows the agent's requests from its `request_restart` tool, checks that the new code loads before it stops the server, and can wait until no tool call runs (**When tools finish**). The owner can set a **Restart command** there, such as a systemd reload, which runs in place of the launcher's restart. The sidebar's light/dark button switches the mode.
- **Lancet Guard.** Off by default: the owner turns it on in Menu → **Extensions**. If `specpi-lancet-guard` is installed in the agent and turned on there too, its rules and classifier check every bash, write, and edit call, and each command the agent starts in the background. A "risky" or "unsure" verdict shows Allow/Deny buttons to everyone in the session; the answer survives restarts. The classifier needs the LANCET Nano model, a one-time download of about 109 MB. While it is missing, the guard row in Extensions says so and the owner gets a **Download** button there: it fetches the pinned release from GitHub, checks it against fixed checksums, and installs it where the agent's own `/lancet-guard setup` puts it, so the agent uses it too. Progress shows in every tab, and nothing downloads it without that button. A guard that is on without its model blocks the bash calls its local rules leave open, and the status line shows "guard failed".
- **Codemode.** On by default, like `"+codemode"` in the agent's `defaultTools`. The `codemode` tool runs JavaScript the agent writes in a QuickJS sandbox with no Node, files, network, or timers; its only capability is calling the agent's other tools as `tools.<name>(args)`. Use it to batch independent calls, chain them, or filter large output before it reaches the model. Each call a script makes goes through the same checks and hooks as a direct call, so Lancet Guard judges it and can ask for approval. `store()` and `load()` keep values per conversation. Its card shows the script, each call it made, and the output.
- **Share to the agent.** With Pia on the home screen (Android), share a link, some text, or a screenshot from any app to Pia: pick a session or a new one, and it goes into the message box with the files attached, ready to send.
- **Questions from extensions.** An extension can ask the person the agent works for on a card, as an approval asks: a sign-in, a one-time code, a key, or "solve the CAPTCHA, then tap Done". Only that person can fill it in (the owner, when nobody is known); anyone who can steer can **Decline**. What is typed goes to the extension, never to the agent, into the transcript, or to the other people here, and the call's line says **Answered** or **Declined** by whom. A notification goes to that person alone, and opens the session: the fields are filled in in the app. Extensions can also hide values (they show as `[label]` in command output, tool results, and in a message to the agent that someone pasted one into), give commands environment variables, and use the session's browser page. Since 0.22.0 ([docs/extensions/people-values.md](extensions/people-values.md)).
- **Approvals need someone else.** An owner setting under Lancet Guard in Menu → **Extensions**: a guest cannot allow a risky call that their own message led to. Someone else has to; the owner always can.
- **Docs for agents.** the agent's system prompt says where Pia's documentation is ([index.md](index.md)), to read when someone asks about Pia itself: changing how the agent works without code, writing extensions (with tested examples), and changing Pia's code while it runs, checked first on a throwaway copy (`node test/serve.ts`).
- **Drop-in extensions.** Put your own extension module (a `.ts` file that default-exports `(host, web) => Extension`, or a list, or nothing) in `~/.pi-pocket/extensions/`. It shows in the Extensions sheet, stays off until the owner turns it on, can import Pia's packages (Pi Durable, pi-ai, the agent's MCP client pi-mcp, and the rest) as the built-in modules do, and reloads when edited. One that would take the name of a built-in extension or tool, or of another drop-in's, is not loaded, and the sheet says why: installing it would replace that one.
- **Extensions in the app.** A module can add to the app itself, without changes to Pia's code: routes on the server, commands for the message box, and a browser module with buttons on the rail, pages in the conversation's place (as the subagents board shows), panels beside the conversation (where the Browser and Files panels dock, with a button in the top bar and the places), items in the status line under the message box (with a short form a narrow line takes), sheets, rows in the menu, and launcher actions, which work without asking the agent. A dashboard of a provider's usage, the server's load, or a machine's power and temperature, say: the route asks the service with a key that stays on the server, and the page shows what it says, live with the module's events. It is the owner's alone unless the module opens it to people who can steer, or to everyone who sees every session; someone invited to one session never gets it. A module can also show **public pages** to anyone with one of its links, with no sign-in (`/l/<token>`, since 0.22.0): each link closes at its time (30 days at most) or after the answers it takes, the page runs in a sandbox with no script, so whoever opens it while signed in lends it nothing, and Extensions says which modules have them ([docs/extensions/public-pages.md](extensions/public-pages.md)). Turning the module off takes away what it added, its pages included; an edit swaps the routes, and an edit to the browser module's files has tabs load it again. One that fails tells the owner why in a notice and in the Extensions sheet, and the rest of the app goes on; a tab opened with `?noext=1` loads none of their browser parts (safe mode), to turn off one that breaks the app. [docs/extensions.md](extensions/app.md) says how, with an example: a page with the server's load, memory, and uptime.
- **Extension workspace APIs (0.16.0).** A page can save its own durable catalog with request-lifetime document commits, or use a source-bound route to start linked sessions as the person who clicked Run. Current source access, turn, plan, spend, team, and model checks apply; explicit thinking choices are not silently lowered. Human history can open authorized sessions through `pocket.openConversation`. Extensions can read the running server's package version through `host.pocketVersion` or browser `pocket.pocketVersion`, without an updater or restart control; the extension API level remains 1.
- **Extensions hub.** Menu → **Extensions** opens **Discover**, **Installed**, and **Updates** for the owner while the gallery is on. Wide screens show the list and selected entry side by side; phones show one at a time, with Back returning to the filtered list. **Installed** (also tap "guard" in the status line) lists Pia's extensions with their tools, the routes, commands, and browser module they add to the app, and any load error, in this browser too. The owner can turn Artifacts, Design, Browser, Subagents, Scheduled messages, Done when, Plan mode, Codemode, Memory, Pia, Triggers, Extension gallery, Pia updates, Agent Teams, Session tags, Lancet Guard, or a drop-in off and on, or reload one; the change applies to every session at once, stays after restarts (`disabledExtensions` and `enabledExtensions` in `~/.pi-pocket/config.json`), and everyone in a session sees who changed what. Turning Lancet Guard off first shows a warning card with **Keep it on** and **Turn off**; only **Turn off** applies the change. This leaves the agent's own setting (`~/.pi/lancet-guard.json`) alone. Under Pia, the owner can set the assistant's display name. The system prompt cannot be turned off.
- **Extension settings.** A module can declare settings (on or off, text, a number, a choice, or a secret such as an API key); the owner changes them in Menu → Extensions under the module, with **Save settings**, and **Default** or **Clear** to put one back. A secret's value never leaves the server: the sheet shows only that it is set. Modules can also listen to what happens in the app (sessions made, renamed, and archived, messages, runs) and offer services to each other; Extensions says which ones offer a service. Since 0.22.0 ([docs/extensions/services-settings.md](extensions/services-settings.md)).
- **Extension gallery.** Menu → Extensions → **Discover** (or **Find extensions** in the launcher) lists drop-ins other people wrote, from a reviewed index ([TannerMidd/pi-pocket-extensions](https://github.com/TannerMidd/pi-pocket-extensions) unless the owner picks another): search them by name, words, and tags; entries for a newer Pia are hidden. Each row has a quiet **Install**. An entry walks through three steps, each with its buttons: **Install** (it stays off), **Look it over** (**View source**, **Ask the agent to review**), and **Turn it on**, which asks once more, in place, before code runs; what it adds shows in plain words, with technical information folded below. In Installed, a tap on a row opens its settings and details, and turning a drop-in on asks in its row. An entry shows who wrote it, where its code is (a GitHub repository at a pinned commit), its files, and what it declares: its tools (and which only read), hooks, prompt sections, wraps, routes, and browser module, and who can reach them. **Install** downloads its files over https from that commit, checks each against the SHA-256 the index pins (one that differs installs nothing), and puts them in the extensions folder, off, as every drop-in starts. Before turning it on, read its whole source in the gallery, or **Ask the agent to review**: a new session in the extensions folder, in plan mode, where the agent audits what the code reads (`config.json`, sign-ins, other secrets), the addresses it calls, the processes it starts, what its browser module does, and whether it does what it declares. Updates are never automatic: the **Updates** tab lists available updates with a **Review update** button, and the review shows what changes, as a diff of every file and of what it declares, before you apply it. When the index revokes the version you have, the gallery and Extensions say why and offer to turn it off, and a notice says so while it is on. **Uninstall** removes its files (where each came from is kept in `<name>.gallery.json` beside it). **Share…** on one of your own drop-ins in Extensions checks that it stands on its own (its files named after it, importing only Pia's packages and its own files), drafts its index entry (the description from its doc comment, each file's SHA-256, what it declares while it is on), asks where its files are on GitHub (the repository and commit you put them in, tags, your GitHub name), and, once the entry would pass the index's checks, opens GitHub's page for a pull request to the index with the entry filled in; Pia itself makes no GitHub calls. [docs/extensions.md](extensions/publishing.md) says how to publish. The owner's alone; turned off in Extensions, it reads nothing. An index that lists themes (from when Pia had them) is still read, and its themes are skipped.
- **Updates.** Pia never fetches, merges, or installs a new version by itself. It asks GitHub for the newest release of the repository in `package.json` 2 minutes after the server starts and every 6 hours after (or the repository's version tags, without notes; `PI_POCKET_UPDATES_REPO` names another), and only reads it. A short notice tells the owner once for each new version: "Pia X.Y.Z is available: Menu → Update Pia." The owner's alone. Menu → **Update Pia** (or the launcher) shows the running version and the newest release with its notes. Only when the owner taps **Start a migration session** does Pia fetch the checkout's `upstream` remote (`git fetch --prune upstream`), then start an agent session for the owner in the checkout, titled "Migrate Pia to …", in plan mode when Plan mode is on. Its first message asks the agent to read what the upstream branch (such as `upstream/main`) changes, find likely conflicts and new packages, and report the commands to merge. The agent changes nothing: it does not merge, rebase, commit, push, edit files, or restart the server. The owner does the merge by hand. The sheet then opens the session, and can start another (noted in `.pocket-update/migration.json`). A checkout with no `upstream` remote starts none, and the sheet says how to add it (`git remote add upstream …`). Beside it, **Sync to main** (only when the owner taps **Sync**) fetches `upstream`, then moves the local branch named after upstream's main (`main`) forward to it: fast-forward only, never a merge, never a push. A `main` with commits of its own is refused, for the owner to merge by hand. When the checkout is on `main`, its files change, edited files stop reloading, and the notice asks the owner to restart the server; changes that are not committed refuse the sync. On another branch, only `main` moves, and the files stay. Under Menu → Extensions → Installed → **Pia updates**, **Look for new versions** (on) turns the look off. The launcher still goes back to the version before when a server stops before it is ready with an update from an earlier version under way.
- **Refresh models.** The owner can tap **Refresh models** in the menu (under App) or the Providers sheet (above Models for subagents), or run **Refresh models** from the Ctrl/⌘+K launcher. The same controls work on phones. Refresh reloads `models.json` and the agent’s sign-ins, and asks configured providers for fresh catalogs. The menu's row says when it is refreshing, and a notice gives the added and removed model counts, without closing the menu; the Providers sheet also shows the errors for individual providers. All connected tabs receive the updated list. Healthy providers finish independently of slow ones; each provider has an eight-second limit. Running sessions keep their chosen models. A local model must be configured in `models.json` or registered by a Pocket-compatible extension: refresh does not load regular the agent CLI extensions or discover arbitrary local servers.
- **Uploads.** In normal chat and Pia, attach files with the picker, paste files or images, or drop them into the message box. Files are saved on the server for the conversation you send to and their paths are given to the agent; supported images also go straight to models that accept them.
- **Rich replies.** Code blocks in the agent's replies show their language and a Copy button, with syntax colors for the common languages (no dependencies, so it works offline), and a block of more than 40 lines folds until you ask for the rest. Some show more than code, with the code a tab away: an `html` block (or a reply that is a whole page) is previewed as a page, inline, with its scripts off and nothing loaded from anywhere; **▶ Run** runs its scripts in the artifacts' sandbox, where it can reach the internet but not the app; an `svg` block is drawn as an image (tap it for full screen); and a `diff` or `patch` block opens in the diff viewer. While the agent is still writing, they show as code. Write cards color the file they write, and the file viewer previews `.html` files the same way, with Run. **Cards in the reply.** An `artifact_inline` call shows as a card in the reply, as the `html` block above with the artifact's name and version in its bar, an **Open** button for the artifact viewer at that version, and the same Preview/Code and Run/Stop; a failed, denied, or stopped call shows as a step with its reason instead. The result records the version its call made, so each card keeps showing its own: an update by the agent adds a new card, and earlier cards, in this session and a fork, do not change. A card's page is read from the artifact's own address, so whoever can see the session sees the card, a viewer and someone invited to this session alone included, and each can Run it. Once run, its page gets what an artifact's does: a follow-up for the message box (a notice for a viewer) and saved state under the artifact's id, shared with the viewer. A preview grows to fit the page, up to 1200 px, and a running page up to 900 px, then scrolls inside. On a phone the bar takes two lines. A viewer already open on an older version stays on it and offers "latest is vN" after an update. Only a call the agent makes itself is a card: one made inside a codemode script is one of its nested calls, and in Pia's panel the call is a line among its steps.
- **Images inline.** Attached images show as thumbnails (also in the composer before you send). When the agent writes `![description](path)` with a path on the server (absolute, `~/…`, or relative to the session's folder), the image shows in its reply. Images a tool returns and SVG artifacts show inline too. Tap any image to see it full screen. Only real image files are shown: the server checks a file's bytes, not just its name.
- **Launcher.** `npm start` asks how your devices should reach Pia: this device only, the local network, a Cloudflare Tunnel, or Tailscale. It then shows the address and a QR code to sign in your phone, and keeps running with keys to restart the server or change access.

## Limitations

- Pi Durable is experimental, and its API can change between releases. Versions are pinned in `package.json`.
- Only one server process can use the database at a time.
- Forks are separate sessions; there is no branch tree to switch between inside one session.
- the agent's own extensions are not supported: Pia runs its own extensions on Pi Durable, and drop-ins from `~/.pi-pocket/extensions/`. The agent's prompt templates work as slash commands.
- A git worktree keeps a session's files apart; it is not a sandbox. The agent can still reach everything you can.
- Artifacts run in an opaque-origin sandbox, so `localStorage` and cookies are unavailable inside them. In the viewer, they can save up to 16 KB of state for each person through the app instead.
- The browser needs Chromium, Chrome, Brave, or Edge on the server. Pages live in memory, so a restart opens each one again at its last address, but not what was typed into it. The default on-disk profile is shared by all conversations and survives page close, browser stop, and server restart; Pi can use an isolated in-memory context instead. A browser installed as a snap (Ubuntu's Chromium) is used only when there is no other; it cannot open files outside your home folder. The list of servers running on the machine is Linux-only. Tested on Linux and macOS; not yet on Windows.
