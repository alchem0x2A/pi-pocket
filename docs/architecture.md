# Architecture

How Pia's parts depend on each other, and the orderings the code relies on. [map.md](map.md) says where things are; this says what to keep when changing them.

## Durable truth and what memory keeps

Pi Durable owns the lasting state of conversations: conversations, entries, tasks, and Pia's documents (`docs.ts`), in `pocket.sqlite`. People and settings, push subscriptions, uploads, and worktrees are files beside it ([map.md](map.md#data-pi-pocket-or-pi_pocket_dir)). What `PocketApp` keeps in memory about conversations is read back from storage:

- At startup, `#recover` reads each conversation's run, agent, chat, subagents, and who the agent works for in it.
- After that, every commit goes through `#committed`, which keeps the memory up to date.

Pi Durable 1.4.0 migrates SQLite storage to schema version 2 when it opens. Older Durable versions cannot open that database. Back up the complete data folder with the server stopped before upgrading to Pia 0.21.0. Pi Durable 1.5.0 keeps that SQLite schema, but writes the `pi.live` document at version 3 (`trigger` in place of `reason` in compactions, and `turns` in a run), and `pi.tool` at version 3 and `pi.generation` at version 2. Pi Durable 1.4 cannot read these, so a server rolled back to 1.4.0 after 1.5.0 wrote to a conversation leaves its tasks blocked. Back up the data folder before the upgrade.

Pi Durable 1.5.0 changed what Pia reads from it:

- **Commits.** `#committed` observes stored commits (`observeCommits`). A document change is tagged: `kind: "change"` with its value, or `kind: "retire"`, which the views read as a document that is gone. Partial answers and tool output are deferred commits, so observers see them only when they are stored (at the end of the answer, a tool's result, or within 1 s). The room's view gets them at once through its watch.
- **The room's view.** `Conversation.watch()` gives a window of the newest 50 to 100 entries of the fork-aware history, not the active context. `Room` (`#watchView` in `room.ts`) keeps the whole active context, as the view did before: the context once from `Conversation.context()`, then each entry the watch adds, a head marker cutting the entries before its head. When a burst moves the window past entries it has not seen (`before` past the newest held), it reads the context again.
- **Failed runs.** `FAILED_RUN` in `app.ts` counts the new `RunFailureReason` values `orphaned`, `interrupted`, `restart_limit`, and `turn_limit` as failures; `nothing_to_answer` is not.
- **Watches.** Listeners get a tagged call (`{ kind: "value", value }`). `taskGraph()` is gone: a read of the task graph takes the first value of `watchTaskGraph()` and stops the watch. `HookApi` gained `entry` and `entries`. Native codemode calls `api.executeTool()`, so nested hooks get their own Durable runtime and history reads. `host.history` provides read-only native `Conversation.agent()` and `Conversation.context()` access for built-in request hooks. `HookApi` itself has neither method. Codemode does not emulate tool hooks.

Scheduled messages, PR watches, repository watches, and Pia reports held while Pia is off use durable `sleepUntil()` checkpoints. A sleeping task holds no invocation and resumes at its saved phase when the harness clock reaches its deadline. The task graph includes these tasks with status `sleeping`.

Some state lives in this process alone, and a restart forgets it. For example:

- who is connected, typing, or away;
- which tool calls wait for approval;
- the browser's pages; its shared profile's cookies and storage remain on disk;
- when each run ended, which peek tiles and session-list squares use, and whether its last run failed;
- provider sign-ins in progress;
- the edit and write calls Changes found in each session's history, so a look reads only the entries added since.

## Who owns what

`PocketApp` (`app.ts`) creates the app's parts and hands each one the app.

**Its parts:**

- `commands`, `extensionCommands`, `collab`, `alerts`, `providers`, `schedules`, `background`, `goals`, `shell`, `spend`, `compactionReview`
- `workspace`, `transcripts`, `attribution`, `piSessions`, `pia`, `watches`, `hooks`, `memory`, `gallery`, `updates`
- `browsers`, `linkedSessions`

**What stays on `PocketApp`** (the parts call these rather than keeping copies):

- **Access:** `canSee`, `requireSee`, `requireSteer`, `requireDriver`.
- **The conversation tree:** `rootOf`, `parentOf`, `conversationsOf`.
- **Where a conversation works:** `cwdOf`, `agentState`, `sessionMeta`, `isBusy`.
- **Live views:** `room`, `openRoom`, `releaseRoom`.
- **Tabs and peek tiles:** `attach`, `detach`, `setPeeks`.
- **The app's lifecycle:** `open` and `close`.

The harness, models, and settings exist only once `#open` has set them up, after the parts are made. So a part made with the app must not read them in its constructor; it reads them when it is called.

The native extension loader registers one scoped resolve hook for drop-in import graphs. Its compatibility namespace re-exports Pi Durable and supplies a delta-only checkpoint predicate for older document definitions. Built-in modules and core imports keep the real package; existing exports retain their identities.

Extensions never see `PocketApp`. They get `PocketHost` (`host.ts`), whose functions call into the app lazily, and `web`, through which they add routes and a browser module to the app. `ExtensionWebs` (`extension-web.ts`) keeps what each module's version added, which the loader commits once the module installed and removes with it, running its cleanups. The required `compaction-review` extension uses `host.compactionReview` to write summaries with a separate model when the owner has chosen one. It does not change the conversation model. Summary usage is committed once with conversation usage and the captured payer. The HTTP layer parses a request, checks it, calls a part, and writes the answer; it holds no state of its own beyond invites and the event streams' pollers. The owner-only `/api/links` route reads Tailscale Serve's MagicDNS HTTP/HTTPS proxy routes, then adds HTTP services from `network-links.ts` and the Browser panel's local-server scanner. It puts valid Tailnet HTTPS links first.

## Favorite folders

`FolderFavoritesDoc` (`pocket.folder-favorites`) stores each person's ordered favorite working folders in SQLite. `folder-favorites.ts` reads and changes only the signed-in person's list; explicit star/unstar operations run inside one harness transaction, so concurrent devices do not overwrite unrelated changes. The commit coordinator sends each connected client only its person's list as a `folder-favorites` event. `hello.folderFavorites` supplies the initial list and refreshes it on reconnect. The folder picker shows only what the server committed, so a failed save leaves its list as it was.

## Linked sessions

`LinkedSessions` (`linked-sessions.ts`, `app.linkedSessions`, `host.linkedSessions` as `LinkedSessionsApi`) starts a session from another and carries messages between them; Agent Teams (`extensions/agent-teams.ts`, off by default) is its only user. A linked session is an ordinary ownerless session in the source's folder. Its session entry's `linkedFrom` names the session that started it, and nothing else follows from it: it is not in `SubagentsDoc`, `parentOf`, or `rootOf`, so it gives no access, and stopping or archiving one leaves the other as it was.

- **Whom it acts for.** Each call acts as the person the agent works for in the source (`requesterOf`), with their checks: seeing the source, steering, the turn, spend, and, to start one, access to every session. The source in plan mode starts and sends nothing. A message goes through `Commands.submit` as sent for that person (a `p:` request id), with `[via linked session …]` and the message fenced (`defang`), so its text is never a slash command and the agent reads it as a request; the target's checks apply there too. The transcript knows such a message by that label and fence, not by the words before the fence.
- **Once.** Each call's key is hashed with the source into an item of `LinkedSessionCallsDoc` (`pocket.linked-session-calls`), which records the session it made or messaged, whom it acted for, and when. A start writes it in the same commit as the session, then sends the first message; a message's request id is made from the same hash, so a replay finds the session and the message it made. Records are kept 30 days, and the newest 1000.
- **Bounds.** A linked session starts none. Since 0.19.0 no count limits how many a session starts (before, at most 10, counted in the commit that made one). `LinkedSessionRelayDoc` (`pocket.linked-session-relay`) on the team's top session counts messages between its sessions, and a person's own message in any of them (`Commands.submit` without a `via`) sets it back to 0. It is counted in a commit before each message goes, so it survives a restart. Since 0.19.0 no send is refused on that count (before, past 20 were). `Spend` counts a team against its top session's budget: the top session, every session linked under it, and their subagents.
- **What it shows.** Sessions know each other by addresses of their own (`LinkedSessionPeersDoc`, `pocket.linked-session-peers`), so no session id goes into a shared transcript; a fork starts with none. `list` reaches only the sessions the person sees, and names them only when everyone who sees the source sees them too. The session list (`PocketApp.sessions`) gives someone who cannot see the origin `linkedOrigin: true` in place of `linkedFrom`; a scoped person's tabs get their own list in every broadcast, not a filter of everyone's.
- **Models.** A start copies the source's agent settings (model, thinking, instructions, tools), not its history. It takes only a model on the owner's list for subagents (with no list, only the source's model); a start that names none gets the source's model when it is listed, and is refused when it is not (`ChooseModelError`: the agent must choose from the list, which the error gives). At the thinking level of the source unless the start names another (any level; the model's nearest lower one when it lacks it), and only after `Providers.problem` asks its provider afresh: nothing is made with a model that is not allowed or cannot be used now.

**Human extension starts (0.16.0).** `web.conversationRoute` resolves its named source and checks the signed-in person before its handler. Its `linkedSessions.start/list` bind both source and person, without changing source attribution. They reuse the same receipt store and message request ids; human replays cannot adopt another person's receipt. Explicit human thinking choices are rejected rather than lowered. Human lists add an actor-visible `conversationId`; host lists remain opaque. Creation copies fresh inherited agent settings on the mutation line and rejects changed source selection settings. Before the initial message, the intended target folder/model/thinking must still match.

`Commands.submit` has a core-only admission lease for this path. After message preparation, linked sessions authorize source/target documents in a transaction and subscribe synchronously to relevant policy commits. The child context passed to Durable's submission cancels on an intervening change. Its cancellation getter also rechecks current actor/access, model allowance/auth, and spend without asynchronous work. Durable checks that context when queued admission enters the mutation line: this is the final admission boundary, not a promise to undo work after admission. The lease is disposed when submit settles, before post-submit bookkeeping. Legacy host calls retain requester selection.

Subagents leave Agent Teams out of every subagent (`extensions/subagents.ts`), even while it is off, so turning it on later gives no subagent a way to start sessions.

## Local session tool discovery

`local-tools.ts` wraps the registry's read interface, not the installed extensions or execution environment. `app.ts` gives this view to the harness for every session, including Pia. The loader still owns the original registry. Each snapshot adds a synthetic `pocket-local-tools` extension. It defers non-base tools and gates known built-in tool guides until a tool is offered. Lessons, policy sections, and unknown extensions' sections remain. Hooks and durable tasks remain active.

The `available_tools` section renders from the resolved agent's offered and deferred tools on each request. It sorts by name and omits loaded status, so loading alone does not churn the catalog prefix. Disabled, excluded, and tools-only registrations stay out. Built-ins use a curated summary map; new registrations can supply local `shortDescription` metadata. Summaries are at most 5 words and 80 characters, with a generic fallback rather than a misleading truncation. No upstream registration changes are needed.

`tool_search` reuses Pi Durable's ranking with exact-name priority and a 10-result bound, but discards upstream's load control. It returns only names, short descriptions, and loaded status. Search has no loading side effect. `tool_load` accepts an explicit list of 1 to 10 exact names and rechecks availability before returning `control.addTools`. An unknown or disabled name rejects the entire batch; duplicate and already-loaded names cause no extra loading. Durable stores loaded names in `AgentDoc.modelTools`, so restart and compaction preserve them. Discovery searches enabled, model-callable, deferred tools, or returns an already-offered exact-name match. This is a token-exposure policy, not a permission boundary: nested tool execution keeps its existing capabilities and hooks. Fresh registry snapshots rebuild the wrappers after extension reloads. No new document kind or storage migration is needed. `PI_POCKET_TOOL_DISCOVERY=off` bypasses the view for rollback and legacy scripted-model fixtures; `test/local-tools.test.ts` exercises the discovery path.

`ls` uses the conversation's file-system capability and bounds its listing. Optional `rg` uses an argument array through the same execution environment, with a timeout and output spilling. Neither creates a second environment or bypasses environment wrapping.

## Pia's private conversation

`pia.ts` owns display-name normalization and the shared workspace helpers. `config.ts` keeps the configurable `assistantName`. A config written by an earlier version can still load; the app ignores its obsolete `assistantProfile` and drops it on the next config save. Pia uses one behavior: normal enabled tools, session-management tools, the shared workspace `<dataDir>/pia`, and one `AGENTS.md` loaded independently of the current folder. Subagents and Background are off by default unless the owner makes an explicit choice. The assistant uses ordinary session compaction through Pi Durable and the required `compaction-review` extension; it has no private summary hook or separate compaction threshold.

`pip.ts` owns the private assistant conversation, its session-management tools, and its follow/report tasks. The module path `pip.ts` and extension id `pocket-pip` stay unchanged for existing sessions and explicit extension records. New session metadata uses `pia`; `assistantOwner` also reads the old `pip` metadata field. The private conversation remains outside the session list and outside other people's access. The extension selection adds only `pocket-pip` to the normal enabled extension set; it does not remove tools. Its shared `AGENTS.md` is created exclusively and never overwritten. Closing the panel does not reset context; Start fresh uses the existing reset operation and keeps stored history, workspace files, and managed sessions.

Stored follow, model-attribution, and compaction document kinds keep their original names for compatibility. The model-attribution and old compaction kinds remain defined, but current code does not read or write them. The browser loads `web/pip.js`; the panel gets a separate room view through `piaview`. The HTTP panel route remains `/api/pip` so existing links and clients do not break. A previous browser extension API name remains as a compatibility alias; new modules use `pocket.pia`.

## Work from outside the app

A PR watch (`watches.ts`) is a `WatchDoc` in its session and a durable task there, which sleeps until its next look, looks with `gh` (`watches.gh`, which tests replace), and puts what to tell the agent in its checkpoint before sending it: the send's request id is the watch's task and count, so a restart sends it once. Comment ids told, and the commits whose failures and conflicts were told, stay in the watch. Webhooks (`hooks.ts`) are app-wide (`HooksDoc`); `/hook/…` is outside `/api` and its sign-in, and lets a post in only by its hook's secret. Both send through `Commands.submit` as their person, with a `via` that marks the message (`[via PR watch]`, `[via webhook NAME]`), so that person's checks and spend limit apply, and what came from outside is fenced (`fence.ts`, as Pia's session text is): no closing tag survives inside, in any case or spacing. A hook's address and secret are checked before its body is read. A signed hook (`signed`, for GitHub) lets a post in only by GitHub's signature: its secret is never in its address, so the address GitHub shows a repository's admins cannot post. The agent's `watch_pr` names a PR by number, which `gh` finds in the session's own repository, or one elsewhere by address only where `gh`'s account can push (`requirePush` in `github.ts`); what follows `--` is never an option.

A repository watch (`repo-watches.ts`) is an item of the app-wide `RepoWatchesDoc` and a durable task in the conversation it messages (Pia's, or a session's), with the same wait, look, and send phases as a PR watch: a look puts the message in the task's checkpoint, and the send's request id is the task's and its count's, so it goes once. It reads the repository's issues, pulls, workflow runs, releases, and comments through `gh api`, and keeps the ids it told. Pia's tools (`repo_watch`, `session_watch_pr`, `session_start` with `repo`) act through `Pia` as its person; a repository is worked on or watched only where `gh`'s account can push, and `Pia.checkout` finds a session's checkout whose `origin` is the repository, or clones it once into `repos/`.

## Who chooses models

People choose the model for each conversation and for Pia itself. Pia can choose a model for delegated sessions or switch a session when the task needs it. Every choice still uses a model available to the server:

- **Sessions** run on the model someone picked, or on what a new session starts with (`Commands.#defaultModel`): the owner's default, even when it is not signed in now, else a trusted project's model/thinking default, else the last model picked, else the agent's global default, else none. `project-model.ts` reads only the final session folder's `.pi/settings.json` at creation, without a cache; a fresh creation-local global-only settings reader supplies defaults and trust policy without changing `app.settings`. It checks the agent's trust store and global trust policy, validates a complete provider/model pair, and keeps known unsigned models rather than silently substituting one. Invalid trusted settings stop creation with a contained error. Thinking-only settings cannot change another source's model/thinking pair. Owner defaults bypass project settings. Imported sessions, forks, subagents, manual choices, and Pia's own conversation retain their previous selection behavior. A model the person explicitly named to Pia bypasses project defaults before its manual configuration step. Trust gained after creation applies only to later new sessions; existing choices never track file or folder changes. Extra project skill/prompt paths and per-project run policy are not supported yet; the shared app settings and older host APIs are unchanged.
- **Subagents** run at their session's thinking level unless the spawn names another, of any height (`extensions/subagents.ts`), on their session's model while the owner's list is empty, and only on a listed model once it is not: the session's model when listed and none is named, else the model named, which is required when the session's is not listed (the refusal lists the allowed models; the prompt section lists them too, each with the facts from `host.modelInfo` that help choose: thinking, context window, price; `model-facts.ts`). The owner may allow models (`subagentModels` in `config.json`: `PocketApp.setSubagentModels` replaces the list, and `allowSubagentModel`, behind `POST /api/subagent-models` that the Providers sheet sends, adds or takes off one model, reading and writing the list with no wait between, so changes that come together all count); with none allowed the tool has no model parameter, and the app rebuilds the module when the list changes. Each call checks the list as it is then: a model not on it (the session's own included) is refused, and so is work for a subagent already on one; a subagent has no `subagent` or `team` tool, so none starts a nested one; a person may raise a subagent's thinking by hand, and work sent to it leaves that level. Before an allowed model is used its sign-in is asked afresh, so a stale mark neither refuses it nor lets it through. A report of a subagent its model or provider failed (by the provider's words: a sign-in, a missing or refused model, a quota) carries the model and tells the agent to stop and tell its person.
- **Linked sessions** (Agent Teams) start on a model the owner allows for subagents (their session's model when it is listed and none is named, else the model named, which is required when the session's is not listed; with no list, their session's model), and get messages from the agent only while they run on one, at their session's thinking level unless the start names another (`linked-sessions.ts`); a model that cannot be used now is refused before the session is made.
- **Titles** use the conversation's own model. **Compaction** uses the owner's optional `compactionModel` override, then the owner's `defaultModel`, then the conversation's model. The required `compaction-review` extension intercepts `beforeCompact`, serializes the selected history with the agent's conversation serializer, and uses the chosen thinking level. The Compact sheet can override this choice for one request, and `/compact --model provider/modelId` does the same. Neither choice configures the conversation, and custom summary usage is counted once. Pia uses the required session hook and the same fallback and per-request choice.
- **Pia** can choose a model for a new delegated session or switch a session's model. `session_start` and `session_model` accept an exact provider/model or a loose name; Pia resolves that name against models available to the server and checks the provider sign-in before use. A person still chooses Pia's own model and the default model for new sessions.
- **Sign-ins:** `Providers` asks subscriptions' sign-ins afresh (the owner's Providers sheet, a model a subagent on another model or Pia is about to use, a run that failed on one, a run answered by a marked one) and keeps, in memory, the ones their provider refused to renew. Only subagents on another model (`resolveModel`, `modelProblem`), Pia, and linked sessions as they start (`Providers.problem`) check before use, and refuse their models. Everything else tries the model: a session's own run and a subagent on its session's model fail where people see them, and a run that failed on an expired sign-in marks it; a title that fails is only logged. `modelList` and `agentInfo` mark them, and the owner is told. A check that began before a sign-in or sign-out here marks nothing.

**Manual model refresh.** `Providers.modelRefresh` (`model-refresh.ts`) shares one in-flight refresh across owner tabs. `POST /api/models/refresh` requires the owner and the normal `X-Pocket` header; `hello.server.refreshModels` gates the UI against an older server. It checks local configuration with the agent’s public runtime API before reloading it, then refreshes each configured provider in parallel with a separate eight-second limit and `force: true` (network stays off under `PI_OFFLINE`). Each completed provider sends the existing `models` event and refreshes room views, so a slow provider does not hold back a healthy one. The agent owns cache publication and cancellation generations; failed catalog fetches keep its cached/static models. Refresh never configures a conversation or changes the default or subagent allow-list. Counts compare available provider/id keys before and after; provider errors are safe fixed messages, not raw exceptions that could contain credentials.

`PocketApp.modelList` resolves the agent’s `enabledModels` through the SDK’s `resolveModelScopeWithDiagnostics` against available models, then `modelList` marks scope membership alongside sign-in state. Both `hello` and providers’ `models` updates use that list. Manual refresh rereads the agent settings before recomputing the scope; malformed scope values are ignored so the picker still opens. The model picker’s Scoped / All state lasts only while it is open and filters the list without changing the agent’s settings, the session’s model, or its default. Empty scopes mean all available models, not a ban on picking models.

## Waiting for a provider's limit

`LimitGate` (`limit-gate.ts`, `app.limits`) wraps `models.streamSimple` after `timing.ts` does, so each attempt is timed on its own. A request that fails before any content on a limit that clears with time does not fail: it waits inside its own stream, and goes on. Pi Durable sees one slow request. `limits.ts` (`classify`) reads the error text, and the status and limit headers that a recording `fetch` saw (a known status decides first: only 408, 429, and 5xx can wait, a 409 only with a reset time in a header, a 403 only in a usage limit's own shape with a reset time), and says one of three things: not a limit (a sign-in, billing, a bad request, a context that does not fit: the error goes on as it is), a limit with a known end (`resetAt`), or load with none (`backoff`).

- **The key.** A limit that covers the account (a Claude subscription window, a ChatGPT or OpenCode Go usage limit) is held by the provider (`provider`), so one canary serves every model. Any other limit (a 429 or an overload, or a cap for one Claude model) is held by `provider/modelId`. The key holds no token (it changes at each renewal) and no counter (it starts again at each start), so a renewal and a restart keep a gate. A sign-in or sign-out here drops the provider's gates (`LimitGate.reset`), and a failure of a request sent before one opens none (`Providers.signInEpoch`, compared within one request).
- **Waiting.** Until the reset (with 5 to 30 seconds added) or, with no time, 15 s, 30 s, 1, 2, 5, then 10 minutes. At most `limitWaitHours` (the owner's, default 6, 0 is off) for a known reset and 30 minutes without one; a reset farther away, or 40 tries, makes the gate give up (`refusing`): that request fails at once with the reset in its text, and for five minutes every request for the key fails at once, so Pi Durable's own three retries cannot start a second wait.
- **The canary is the real request.** A request the provider rejects costs nothing. One waiter sends it. When it gets content, the gate opens and the others leave one at a time, 1 to 5 s apart. A failure that is not a limit, or a Stop, frees the next waiter to try. Retry now (`POST /api/c/:id/limit/retry`, for whoever may see and steer the session) sets the gate due. A failure after content started is never replayed; Pi Durable retries it as before.
- **Durable.** Nothing here is stored as the truth. A restart replays the generation's `request` phase, which meets the limit again and waits again. `provider-limits.json` keeps the gates so that each waiting session does not send a rejected request first. It keeps a gate's first time (`since`) and a refusal with its end, so a restart does not start a wait again: a gate that nobody waits at, whose deadline passed (a stopped wait, or the server was down), does not refuse: it lets one request go as canary at once and keeps its first time, so a canary that meets the limit again gives up and no new full wait starts. One whose retry time passed but whose deadline did not tries at once too. A request also keeps its own first time and try count across every gate it moves through (a scope that changes does not start the wait again). It is a hint: a missing, damaged, or odd file means no limit is known. A close aborts every nap through the run's signal, so a close writes no failure, and Stop and Interrupt end a wait at once. Pia sets `restartLimit: Infinity` to turn off Pi Durable 1.4's crash-loop guard. Its task phases can wait for hours without changing state, so repeated unclean stops must not park them. This keeps the 1.3 behavior; the launcher already delays repeated server restarts. The wait can move to a Pi Durable retry decision hook later with no change that people can see.
- **No spend, no model choice.** A wait sends nothing but rejected requests. A gate never picks another model: only people do. Titles and Pia's summaries pass `noWait` and fail as they did.
- **What people see.** The room view's `live.limit`, the session list's `limited` (a session's subagents too), the peek summary, and a subagent's `limited` on its bar and the board: the live line, the square (`limited`), peek tiles, and one push (kind `limit`) when a wait of ten minutes or more begins.

## Prompt cache keeper

`CacheKeeper` (`cache-keeper.ts`, `app.cacheKeeper`) wraps `models.streamSimple` as the outermost wrapper, so it sees each real request finish and replays it through the wrappers below. The order, innermost first, is the final payload observer, request shaping, `timing.ts`, `LimitGate`, then the keeper. A warm request passes `noWait`, so a limit makes it fail and never queue. It is on by default; `PI_POCKET_CACHE_KEEPER=off` turns it off.

- **When.** A request that ended in a tool call is replayed with `maxTokens` 1 at 90% of the cache lifetime, or 10 seconds before its end, only when the expected savings are more than the cost. It never warms an idle session, a 1h cache, a request with `cacheRetention` none, or Anthropic thinking set by a token budget.
- **Payload.** The observer hashes the real request's final JSON after all shapers. Before transmission, it compares each warm's final JSON with that hash. Only provider output-cap fields may differ. A changed or unobserved payload sends no warm and adds no spend.
- **Stop.** A real cached request, the end of the run (Pia's too), a changed payload, an error, shutdown, or 30 minutes stops it.
- **Spend.** A warm request's usage counts in `pi.usage` and in the spend of the person and session captured when it started. `Spend` checks their limits before each warm.
- **Restart.** A restart discards the warm timers. It replays no warm request.

## Owner idea inbox

`OwnerInbox` (`inbox.ts`, `app.inbox`, internal `host.pia.inbox`) keeps each owner's ideas in the additive `pocket.owner-inbox` document. Capture only stores data. It never submits a message, creates a session, or starts agent work. `GET` and `POST /api/inbox` support signed-in browsers and bearer-token clients. Browser requests send `X-Pocket-Account`; a cookie for another account cannot synchronize the old account's notes. The API rechecks the current owner role. Archived notes remain recoverable; default lists exclude them.

The owner's private front-page Pia gets an explicit `inbox` tool through the Pia extension. It lists, archives, and restores notes. Execution checks reject ordinary sessions, subagents, other people, ordinary sessions, and subagents. The app rebuilds the Pia tool registrations when the extension changes. Tool results fence note text as data. The `pia_inbox` prompt section adds only the durable pending-note count for the owner's private Pia. It is absent at zero and for ordinary or shared sessions, and subagents. Counting uses the durable private-helper mapping and rechecks access; it never copies note text into the prompt. A previous server host omits the section until restart. Reading a note grants no authority to execute it.

Only **Continue in conversation** creates a normal idle conversation. The new conversation, its receipt, and the original note's archive commit together. A retry returns the same conversation. The browser seeds its composer with the note text; it does not send the draft. The session uses the normal server default folder, not a folder inferred from the note. The owner can use `/cwd` before sending.

`web/quick-notes.js` keeps a per-account local queue under `pocket.quick-notes.v2.<account>`. The panel shows pending ideas and exposes only Continue as a note action. A collapsed note is clamped to 3 lines; the existing note tap reveals its full text inside the scrollable panel. Its compact mic reuses `useDictation` and `MicButton` from `web/voice.js`. The spoken text goes into the existing draft and only the explicit Save action captures it. Closing the panel, navigating, switching accounts, or saving stops recognition. It does not expose archive controls or a view toggle. Reconnect synchronizes the inbox only. `syncStatus` reports the last failed attempt without clearing its reason during retries. Its account-specific `<queue-key>.sync-status` local-storage record preserves the reason across reloads and server restarts. The panel shows an unsynced count and a small failure detail only when needed. HTTP 404/405 identifies an unavailable endpoint; network failures and other HTTP refusals remain distinct. A successful full sync clears the failure. `web/inbox-sync.js` runs background synchronization independently of the panel and rail. A phone conversation with its drawer closed therefore keeps its retry service. Connection, online, visibility, focus, page-show, and storage events supplement a 15-second interval. REST inbox requests do not require an open event stream. Requests and account revalidation have a 10-second timeout. A missing or changed account hint requires bounded fresh account confirmation, never a transfer of cached notes to another account. Local archive changes also wait for synchronization. Web Locks serialize local storage mutations across tabs. An IndexedDB write transaction provides the fallback lock; capture fails visibly if neither lock service is available. Migration uses the same lock, and capture waits for persistence before it clears the input. Migration merges missing legacy IDs even when the v2 cache already exists. It runs during initialization and local mutations, including each sync pass, so later writes from an older tab are not stranded. Legacy cached notes migrate as local ideas; legacy chat-delivered notes migrate as hidden archives. Existing archives and conversation receipts win over legacy copies. The original cache remains intact. Each queued ID gets at most 1 capture attempt per pass; an older failed upload or archive change cannot block a newer capture. Only an acknowledgement for the same ID and text marks a capture synced. Archive acknowledgements must also match the requested state. Request-time snapshots prevent older responses from overwriting newer local completions. Concurrent archive/restore API mutations still follow server commit order. A missing server-list record never discards a cached idea; the service retries the capture instead. A damaged legacy cache remains intact and does not block valid v2 captures.

It never caches conversations or authenticated API responses. Online shell assets remain network-first; the installed fallback is a versioned snapshot. Bump `OFFLINE_CACHE` when changing its assets so installed workers refresh that snapshot. The worker installs during normal online use, without a manual PWA installation. Its cached shell is needed for offline navigation, not for inbox synchronization from an already loaded panel. The running server must include the inbox routes; editing their source files does not activate them without a restart. The offline screen requires an explicit unlock of the last confirmed local owner. Logout, a 401 response, and a confirmed non-owner clear the account hint. ## Memory

Notes (once called lessons) are one document for the whole app, `MemoryDoc` (`pocket.memory`), by id. Its kind, scope, and version are unchanged: a note is a `Lesson` record with optional new fields (`title`, `revision`, `purpose`, `modelRule`, and `title` in a `proposal`). A record stored before notes has none of them and reads as revision 1, with its body's first line as its title; nothing rewrites it. Each note is for a project or for everywhere. A project is keyed by the real path of its git common folder (`git rev-parse --git-common-dir`), so a repository and all its worktrees share notes; outside a repository, by the folder itself. `Memory` (`memory.ts`) works out a folder's project (kept a minute per folder) and keeps the rules:

- A body is Markdown: lines kept, invisible characters and trailing spaces removed, tabs made 4 spaces, at most 1 blank line in a row (`clean`). The limits are 4000 characters for a body and 120 for a title (`MAX_LESSON`, `MAX_TITLE`); a longer one is a 413, never cut. A title stays on one line (`flat`).
- The memory extension's section renders, before each request, 4 lines: a count of the notes the conversation can find, and the rules (search with `note_search` at the start of a task and before an action a note can cover, read with `note_load`, a note is data and can be out of date, save with `memory` only when a person asks or a note clearly helps many later sessions, and the owner approves). No note body is in it, so reading a note leaves the system prompt and its cache as they were. Pia has no project: it finds everywhere's.
- `search` ranks approved notes the conversation can find: every word of the query must start a word of the title or body (title words count 3 times, an exact id or title 10, the whole phrase in the body 5); with no note that has every word, it returns the notes with the most of them, marked partial. `read` returns approved notes by id; an id the conversation may not find is "missing", whatever the reason. A pending note, or a proposal, is never returned.
- `note_load` only reads: its one parameter is `ids`. A compaction would drop what the agent read, so the memory extension's `beforeRequest` hook (`GenerationTask`) puts 1 user message right after the compaction summary: the notes the session read with `note_load` before it, each with its id, title, and current approved text. `Memory.readBeforeCompaction` finds IDs in old direct `note_load` results and native codemode metadata before the context's head marker, back to a reset. The hook scans the actual head and uses the current native agent cwd to resolve scope; it does not cache by summary length or keep an old project scope. A forgotten, pending, or out-of-project note is left out. The message is not stored and is not in the system prompt: it is the same while the notes are the same, so the prompt cache stays valid. `note_load` and `note_search` are replay-safe. Direct mode offers them from the start; Only calls them inside codemode.
- Pins are gone. `NotePinsDoc` (`pocket.note-pins`) stays defined for stored records, and nothing reads or writes it: a session with old pins loads, and its pins are ignored.
- the agent proposes, the owner approves. Every note the agent saves, and every one a person who is not the owner saves, is pending: nothing finds it until the owner approves it, as what the agent read anywhere in its context could have talked it into one. The agent's (or a guest's) new text or title for a note in force, and the agent's forgetting one, are a `proposal` on the note, which stays as it was until the owner approves or discards it. The tool's result names the note (`details.lesson`), so the transcript offers Approve and Discard under the call. An approval names what it saw (`POST …/memory/:id/approve` with `{ text, title }` or `{ forget: true }`); when what waits differs, `change` answers 409. An older tab sends no title: that holds only when no title waits. An approved change to the text or title adds 1 to `revision`. Pending notes do not count toward a project's or everywhere's cap (200 each); approving one does. Only the owner, or whoever saved a note, changes or removes it, the agent included (as the person it works for).
- `POST …/memory/:id/purpose` is the owner's: `{ purpose: "model-choice", models?, minThinking? }` marks an approved note for everywhere as Pia's model-choice guidance (and unmarks any other); `{}` unmarks it.
- Every write adds an activity line to the session's chat in the same commit. `#committed` tells `Memory` when the notes changed; it sends tabs a `memory` event, and the Memory sheet and menu fetch the notes again (`GET /api/c/:id/memory`).

**Pia's model-choice check (`pip.ts`).** `Pia.start` and `Pia.setModel` call `#checkChoice` before anything is made or changed. Without a marked note (`Memory.modelGuidance`) it does nothing. With one, the call needs a guidance code that Pia got with the note's current revision in the last 10 minutes; otherwise it throws with the note, the signed-in models and their thinking levels, the default model for a start without one (`Commands.defaultModel` for the final folder), and a new code. The code is kept in memory (a restart asks again), is spent by the choice it guided, and goes stale when the revision changes. With a valid code, an optional `modelRule` is checked against the effective level: `clampThinkingLevel` of the model and the level asked (or the session's level for a switch, or the default's level for a start). A start without a model whose real default differs (a worktree's project settings) is checked again after creation; a refused one keeps the session but blocks its first `send` until `setModel` succeeds. `session_model` keeps its result in a memo, so a replay does not switch again; `session_start` already kept its session in a memo.

The App menu exposes the storage path `<dataDir>/pocket.sqlite`; the Memory settings sheet opens the note editor for a selected session. Notes stay in the durable `pocket.memory` document and must not be edited in SQLite directly.

**Instruction files.** `/api/instruction-files` is owner-only. It lists the global and currently loaded the agent context files from the session folder chains, plus the standard global `AGENTS.md`, each with its absolute path and on-disk text. `PUT /api/instruction-files` saves only a path in that fresh allow-list, without following a file symlink. The Settings sheet lists and edits each file. The route also reports the Memory database path.

**Pia's pending queue.** `GET /api/c/:id/memory?pending=all` lists new notes and proposed edits or forgetting across every project and everywhere. It requires the human owner and their private Pia root as its anchor; queue approvals and discards use the same query on the existing mutation routes. The agent writers, other people, shared-session anchors, and queue add/edit/remove requests are refused before cross-project lookup. Approval retains the existing compare-with-what-was-shown check, limits, and transaction. Activity stays in the private Pia chat, not a shared session. The queue response has `pendingAll: true`, no project or add/edit controls, and project labels on lessons; an older running server's scoped response has no marker, so the new UI asks for a restart rather than claiming to show all projects. Browser memory fetches are keyed by person, role, conversation, and view, and refresh on memory events or a new connection.

## Startup

`PocketApp.#open` runs in this order, and the order matters:

1. Take the data folder's lock. Set up push, the agent's settings, and the HTTP settings for provider streams. The pid-only `harness.lock` keeps older readers compatible; its `.identity` sidecar binds the lock file to Linux process start time and boot ID, with age-based recovery for damaged files and Linux process-start checks when identity is unavailable.
2. Load the models, and register the core tasks and every extension module that is on.
3. Open the storage and the harness.
4. `#recover`:
    - read the session list;
    - for each conversation, in turn: its run, agent, chat, who the agent works for (`attribution.recover`), and its subagents;
    - then write back, in one commit, the authors that a crash kept out of the authors documents (`attribution.repair`).
5. Load spend.
6. Subscribe to commits, approvals, and browser pages.
7. Warm Lancet Guard.
8. Resume the work the last process left unfinished.

Work resumes last, so that everything that follows commits is listening before the first one comes.

## The commit coordinator

Pi Durable publishes each commit's changes in no set order. `#committed` handles them in two passes:

1. **Usage first** (`spend.usageChanged`): what a commit's usage cost belongs to whoever the agent worked for before a message in the same commit changes that.
2. **Then each change:**
    - Document changes go to `#documentCommitted`. It tracks busy and ended runs, agents, the session list, and the documents the rooms show (`ROOM_DOCS`).
    - Submissions go to `attribution.submissionCommitted`.

Everything here is synchronous. A commit listener may not call the harness's session APIs, so a write it causes (noting a message's author, or moving a session up the list when the agent starts work there) runs in `setImmediate`. Keep this one coordinator: separate listeners would make their registration order a billing rule nobody can see.

Updates to tabs are coalesced:

| What                                                                       | How often, at most |
| -------------------------------------------------------------------------- | ------------------ |
| A room's changes                                                           | Every 90 ms        |
| Peek tiles                                                                 | Once a second      |
| The session list, and every subagent to tabs that show the subagents board | Every 400 ms       |

Each room update sends a tab its new entries, the live run, and some small fields. The fields that grow with the session, such as the queue, authors, reactions, and pins, go again only when they differ from what the tab has, because a turn sends an update every 90 ms. The queue sends the first 500 characters of each waiting message's own text (not the files it mentions, and not images: a message of images alone says how many), and the names of the subagents in a message of reports. Its row shows one line, and a paste or a batch of reports can be megabytes.

The message the agent is writing goes as what changed since the tab's last update (`liveMessageDelta` in `projection.ts`, put together by `web/live.js`): the blocks the tab has stay, and the block that grows sends only its new characters. A whole message each time made a long answer cost its length squared. The server keeps the blocks each tab has (`Client.liveBlocks`) and forgets them with each full view, which sends the whole message. Events reach a tab in order on one connection (long polling sends again what a lost answer carried), and a new connection starts with a full view, so a change always fits. One that does not, which should not happen, makes the tab connect again.

A tab's connection names what its code understands (`p`, `PROTOCOL` in `web/store.js`). 2 keeps the queue when an update leaves it out; 3 takes the message as what changed; 4 takes a full view with only the newest entries. A tab below 3 gets the whole message with each update, and one that names none (older code, as a tab asleep through an update keeps) also gets the queue with each update, because its code drops a queue that an update leaves out.

A full view for a tab of protocol 4 has the order of every entry in the active context, but only the entries of the newest 80 rows (`firstEntries` in `projection.ts`), with the turn the oldest of them is in, so the tab knows which groups are open there. The tab draws 60 of the rows, and the panel for Pia draws 80. Earlier entries come from `GET /api/c/<id>/context?before=<entry>`, with `rows=<n>` or `from=<entry>` (`Room.entriesBefore`, `loadEarlier` in `web/store.js`), when the person shows earlier messages, opens Find, or jumps to a message that is not loaded yet. The server marks the entries it left out as sent, so an update does not send them. A full view of the same session, as after a reconnect, keeps the entries the tab loaded. A session of 6,000 entries was one event of 8 to 10 MB: on a phone, the tab stopped for most of a second each time to read it, and only its last rows are drawn.

A tab of protocol 5 gets those entries light at first (`lightEntry` in `projection.ts`, marked `partial`): without a thought's words, with a tool's input and output cut to their first 300 characters, and without large details. That is what shows only when a step is opened, and most of a session's weight: the first view of a long session goes from hundreds of kilobytes to tens. The server does not count a light entry as sent, so the update right after the first view (`Room.push`) brings it whole. A long poll answers the first time as soon as the first view is built, so the whole entries come in the next answer. Until then, a call's line may say nothing of its outcome (a result of 300 characters or fewer, with small details, is never made light: it comes whole, so its line can show it), and a thought does not open.

The session list goes to a tab only when it differs from the one that tab last got (`Client.sessionsSent`): it is large, and it is worked out again for many changes that leave it as it was.

## Who the agent works for

A message to the agent names its person in its request id (`requests.ts`):

- `u:<user>:<key>` is a person's own message.
- `p:<user>:<key>` is one sent for a person, such as a scheduled message or a subagent's task.

`attribution.ts` notes each one in the conversation's authors document. The agent works for whoever wrote the newest message (`requesterOf`). A subagent works for whoever its parent worked for when it sent the subagent its last message. Spend, approvals (the "someone else must allow" rule), schedules, and subagents all ask `requesterOf`. A message sent for someone must carry that person in its request id. One that names nobody does not change whom the agent works for: the agent goes on working for whoever it worked for before. Spend, when nobody is known, falls back to whoever started the session, then the owner.

## A request

`http.ts` routes by the first path segment, and turns whatever a route throws into an answer: an `HttpError`'s status and message, or a logged 500.

`/api` (`http/api.ts`) checks, in this order:

1. who is signed in (the cookie, or a bearer token);
2. it notes the quick tunnel a guest came through;
3. the `X-Pocket` header, on everything but GET.

A conversation's routes (`/api/c/:id`) run only after `requireSee`.

`/api/x/:module/…` (`http/extension-routes.ts`) is an extension module's own route: after the checks above, and the `X-Pocket` header on a GET too (a module's GET may change things, and the cookie goes along with a link from another site), it answers only the people its `access` lets in (`mayUse`: the owner by default; never someone invited to one session). The header is checked before the route is looked up, and a route someone may not use is not there for them (404, and a 405 names only methods they may use), so nobody learns of routes that are not theirs. A `:name` part that decodes to `..` or holds a backslash or NUL is a 400. Only the owner reads a 500's words, but for those a module gave `web.error`, which it chose to show. `/x/:module/:rev/…` serves its browser module's files, outside `/api` but after a sign-in, to the same people: one file, or a folder's regular web files up to 8 MB, never its `.ts` files, hidden files, `node_modules`, or anything reached through a link. Each is opened without following a link or waiting (`O_NOFOLLOW | O_NONBLOCK`), and read only when its handle is a regular file and the file that was checked (the same device and inode, and on Linux the path `/proc/self/fd` gives), so nothing swapped in after the check, a folder on its way included, is read. Where there is no `/proc` (macOS), a folder swapped for a link within the check itself can still lead elsewhere: only someone who can write in the module's folder can do that, and they can already run code in the server, by editing the module.

Since 0.16.0, `extension-request.ts` gives each route fresh `snapshot`, `context`, and `commit` capabilities. They re-resolve the current person; viewers cannot commit, and disconnect or handler return cancels them. A commit checks again after an awaited callback so a detached write cannot outlive the request. These APIs are for module documents, not core state. An unbound catalog save has no source turn, plan, or spend policy. Bound GET routes require source visibility, and bound mutations/commits also require steering and the turn. The bound request exposes authoritative source metadata for previews and actor-bound linked-session starts/listing.

The host's `pocketVersion` and `hello.server.pocketVersion` come from `versions.ts`'s startup-loaded package data. Browser `pocket.pocketVersion` reads that metadata, never disk or an updater; `pocket.version` remains the API level. `pocket.openConversation` calls normal `store.navigate`, retaining Back and server access checks.

Where the other checks live:

- **Commands and collaboration** check steering and driving themselves (`requireSteer`, `requireDriver`). They are called from routes, from tasks, and from each other.
- **Owner-only settings** are checked in `http/api.ts`: extension modules, provider sign-ins, restart. Changing people's access, the approval rule, the default model for new sessions, and the models subagents may use is checked in `app.ts`.
- **Invites** are checked in `http/api.ts` too: viewers and people invited to one session cannot create them, and only the owner makes an owner invite. An invite lasts one of `INVITE_MINUTES` (`auth.ts`; an owner invite, always 15) and is kept in `config.json` by its code's hash, so a day's or a week's outlives a restart. Only whoever made one ends it early (`POST /api/invite/cancel`), as the invite sheet does with the one it showed when its settings change, and with one that answers after it closed. One person keeps at most `MAX_INVITES` (`config.ts`) live, their oldest ending first; removing someone ends theirs, and a new owner token ends owner invites not yet used.
- **The workspace's path helpers** (`conversationFile`, `readableFile`) leave seeing the conversation to their caller. Downloads reuse `readableFile`, open without following a final symlink or waiting on a pipe, and verify the opened file against the authorized path and inode before streaming. The owner-only Emacs POST uses the same workspace path policy. `emacs.ts` calls local `emacsclient` with an argument array and a quoted literal filename, suppresses file-local evaluation, and selects an existing terminal frame. It never starts an editor. `network-links.ts` resolves the WeTTY HTTPS address from Tailscale Serve's backend-port mapping.

Each browser tab is a `Client` (`room.ts`), fed by an event stream or by long polling (`http/events.ts`). On connecting, a tab gets:

1. `hello`;
2. the session list;
3. then, when it shows a conversation, the room's full view;
4. then only what changed.

**Compression and caching (`http/compress.ts`).** Text answers of 1 KB or more (`send`, so JSON, and long-poll answers) go in brotli or gzip, as the request's `Accept-Encoding` allows. An event stream has one compressor for its life, flushed after each event and each ping, so every event reaches the tab at once. `keepsUp` then counts the compressed bytes that the response holds (what the tab took), plus text not yet compressed. The stream keeps `no-transform`, so a proxy leaves the bytes alone. The web app's files (`serveFile`) are `no-cache` with an `ETag`, a hash of the bytes: an unchanged file is a `304`, and an edit changes the hash at once, so a tab never keeps a stale module. The bytes are read and compressed again only when the file's size or times change, and the compressed bytes are kept in memory for each encoding. The app page lists every module that `app.js` imports (found from the files as they are now, so an edit or a new import shows at once) as `modulepreload` links, so the browser fetches them all together, not level by level.

## The session list's extension points

`pocket.sessionChips`, `sessionSearch`, `sessionFilter`, and `sessionAction` (`extension-ui.js`) are kinds of what a browser module adds, kept and taken away as rail buttons are. `sessions.js`, `sheets/session.js`, and `launcher.js` read them as they draw: `sessionChips(session)` and `sessionWords(session)` call each module's function for one session, `sessionFilterTest()` joins the filters that are on (null when none is), and `sessionActions()` lists the actions this person may use (`access`); the first with an icon is also a button on rows. New in the list's head opens the folder picker with `fromList`, and once the session is made, `sessionStarted(id)` gives it to the filters that are on (`started`). Only the first 3 filters show and count, so the search field keeps its room. A sheet that a filter or an action opens rises over the drawer, which stays. Each module function gets a frozen `{ id, title, cwd, archived, updatedAt }`, made once for each version of the session that the server sent. One that throws stops its module after the draw, so the list draws without it. A change to what a module added bumps `extensionsRev`, which draws the list and the launcher again; the session list draws again only when a store key it reads changes (`drawnFor`, below).

On the server, `WebRequest.sessions()` (`http/extension-routes.ts`) is `app.sessions(user)` for the person as they are when the handler asks, cut to `{ id, title, cwd, archived, updatedAt }`: modules check session ids with core's own rule of who sees what. Session tags (`extensions/session-tags.ts`) adds nothing on a server older than 0.20.0 (`host.pocketVersion`): such a server, running when its checkout moves to this file, would turn it on, with none of what it needs. It keeps its tags in its own document, gives each person only those of the sessions they see, and changes them in one commit, all or nothing.

Public links (`public-links.ts`, since 0.22.0) are the one way a module answers people with no sign-in. Core keeps the links in `pocket.public-links`, each with its module's name, so `web.links` reaches only its own module's, and `http/link-routes.ts` answers `/l/<token>` only while that module is on (`ExtensionWebs.publicPage`). Core, not the module, closes a link at its time and counts its uses: a use is claimed in a commit before the handler runs, so two posts at once cannot both get in, and given back when the page refuses the post. Every page goes out with a sandbox policy and no script, so it has an opaque origin and the app's cookie gives it nothing. Ask someone (`extensions/ask-someone.ts`) is built on it, with nothing of Pia's but types, as a drop-in would be.

People's values (since 0.22.0) go around the agent, never through it. `host.ask` is an approval with a `form` (`Approvals`, so it waits, notifies, and shows as one): the request that tabs see holds the fields, and the values come only in the answer to the asker, after `answerApproval` checked each field and that the person answering is the one the agent works for (`cannotAllow`). `host.commandEnv` and `host.hide` act in `wrapEnv` (`hidden.ts`), the execution environment the harness builds for each conversation, so bash, `!` commands, codemode, and checks all get the variables and lose the values the same way; an `afterTool` hook of `pocket-core` takes hidden values out of every tool's result before it is stored. `host.browser` (`extension-points.ts`) wraps a `BrowserPage` in a handle with no `evaluate`, and only while the Browser module is on.

Extensions also hear the app and build on each other (since 0.22.0). `host.on` (`app-events.ts`) is fed where the app already learns of each change: session events from the commits of `pocket.sessions` (`#sessionEvents`, comparing the list before and after), runs from `pi.live` going busy and idle, and `message.sent` at the end of `Commands.submit`. A listener runs in a microtask with a frozen copy, so it can neither slow nor change the work. Services (`web.provide`, `web.use`) live on each module's `WebPart`: `use` reads the version that is on now, and `onService` listeners hear a provider's commit and removal. Settings (`web.settings`) are declared on the `WebPart` too, their values kept in config.json (`extensionSettings`), which is read before modules load; the owner's route checks each value against the fields (`extension-settings.ts`), and then the module (`onSettings`) and its tabs (`pocket:settings`) hear it.

## Extensions' commands

A module registers its commands with `web.command` while it loads. `ExtensionWebs` keeps them with the module's version, as it keeps routes: they count once the version installs, a version that fails leaves the ones before, and turning the module off removes them. Each registration has an id that is new with each version. `hello` lists the commands a person may run (`server.extensionCommands`, without handlers or files: viewers none, guests the conversation ones), and a change to them sends everyone's tabs `hello` again.

`POST /api/c/:id/extension-commands` goes to `app.extensionCommands` (`extension-commands.ts`), not to `app.commands`, which sends messages to the agent. Before a run's task is made, it checks seeing and steering, then driving for a conversation command or the owner for a global one, and that the person has fewer than 4 runs going; a retry of a request checks its person again. Nothing refuses a run once its task is made. The wait ends when the browser stops waiting; the run goes on.

A run is a `pocket.extension-command` task (`COMMAND_TASK`), made in one commit with its request id in the person's `pocket.extension-command-request` document for that session (`CommandRequestsDoc`), which keeps the last 100 finished ones and every one still going. A retry finds that task and waits for its result; the same id with other arguments or another registration is a 409. The handler the request chose is kept in memory until its task takes it. The task marks that it started before the handler runs, and keeps the result in a memo: after a restart, a task with no result reports that it was cut off, and its handler never runs again. A handler's own error words go to the owner in a notice; the person gets them only from `web.error` or an `HttpError`.

A card is a `pocket.extension-command` entry with only `kind` and `data`: no `model`, `head`, or `edits`, so the agent never gets it. Its write's request id is the task's, with no person's prefix (`requests.ts`), so it does not change whom the agent works for. A notice goes back only in the answer to the person who ran it.

In the browser, the composer keeps a command's request id while its send is unresolved, as for `!` commands: sending the same text again after a network error or a 5xx finds the same run. Running now names the command from its task, never its arguments, and shows global ones to the owner alone.

## The web app

Plain ES modules, served as they are, with no build. Editing a file under `web/` reloads every open tab, and a syntax error blanks the screen for everyone.

**Loading order matters.** `store.js` is the root, and a few modules do work when they load (listed in [map.md](map.md#web-web-preact-and-htm-no-build)). `theme.js` must load before anything that reads `prefs()` as it loads. `store.set` calls subscribers in the order they subscribed. When moving code between modules, keep both orders. `back.js` sits under `store.js` and imports nothing of the app's, so anything may use it.

**Drawing while an answer streams (`app.js`, `ui.js`).** Every `store.set` draws the app again from the top, once per microtask; components read `store.state` as they draw. A streaming answer changes `view` (or Pia's `piaView`) several times a second, and the chat, people, and the connection change too, so what is big and reads little of the store is wrapped in `drawnFor(keys, component)`, which draws it again only when one of `keys` changes: the session list and the rail (`LIST_KEYS`, `RAIL_KEYS` in `sessions.js`). Its keys must name every key it reads as it draws, and every key that the functions it calls read (`prefs()` reads `appearance`, `canSteer()` reads `me`, `isPinned` reads `pinned`); a key left out shows stale data until another change draws it. `store.set({})` still draws it. Inside the list, each row is memoized (`memo`, compared by its props): the list works out what a row shows and passes it, the row reads nothing of the store, and a minute tick (`useMinute`) and `extensionsRev` draw rows again as their times and extensions' chips change. The server sends `hello`, the session list, and the people again on each connect: their handlers keep what is the same (`kept` in `store.js`), and set nothing when nothing changed, so a reconnect draws only what changed. The server's clock in `hello` (`server.now`) is no change: it goes to `serverClockOffset()`. On narrow screens the sidebar and the home screen's splash are not drawn, and on touch screens rows draw no hover buttons (`WIDE`, `NO_HOVER` in `ui.js`, the same queries as `style.css`; a change draws the app again). Markdown still growing (`cache={false}`) is drawn block by block (`liveBlocks`): each top-level block keeps its HTML from the update before unless its text changed, so an update parses, sanitizes, and colors only the last block. The blocks are found again in the whole text each time, so a later line that changes an earlier block shows; a reference link defined in another block shows as written until the text is whole, and an HTML block with a blank line inside it shows split until then.

**Palette and mode (`style.css`, `theme.js`).** The app has one violet palette, with semantic colors derived from Rosé Pine, as the `--o-*` variables in `style.css`. `:root` holds the dark mode (deep violet surfaces and lavender accents). `:root[data-mode="light"]` holds the light mode (near-white lilac surfaces and plum accents). Contrast follows Modus Vivendi and Operandi: body text at 7:1 or more, and every color used as text at 4.5:1 or more. The page has one cascade layer, `pocket`: `style.css`, and extensions' stylesheets, which `pocket.style()` imports into it after. A stylesheet added outside the layer (a `<link>`) would beat the app. The person's choice is the pref `mode` (`auto`, `light`, or `dark`; `modeNow` gives the mode in force, and `auto` follows the system's setting). `theme.js` writes it to `data-mode` on `<html>`, with the other switches `style.css` reads from data attributes, and keeps a cache in `pocket.themeCache` that `index.html` paints from before anything else shows, so a reload never flashes the other mode. Old prefs from when there were themes (`theme`, `look`, `wallpaper`) are dropped on the next save. Script that depends on where a region is laid out reads it (`useSide` in `ui.js`) rather than assuming the sidebar is on the left.

**Message times (`transcript.js`).** Completed replies show the stored message timestamp projected as `at`, using the same clock correction and formatting as user messages. The `core:time` reply-slot item puts it before React by default; Layout can hide or move it. It is the message's time, not a provider cache-expiry estimate.

**Live thinking (`transcript.js`).** `theme.js` owns the browser's opt-in; the tab keeps each session's disclosure state. Only an open disclosure selects and draws a thought, memoized separately from the live timer. The active generation, or the latest saved response in the current turn during tools, is authoritative even when it has no thinking. Response and block identity reset follow-scroll for a new thought; only that response's handoff to storage keeps the reader's position.

**Launcher openings (`app.js`, `launcher.js`).** `LauncherHost` observes store transitions synchronously, before Preact batches renders, and keys each logical opening separately. A rapid close/reopen therefore gets a fresh query, selection, and theme-commit flag even when the outgoing launcher is still present for its fade-out. The launcher focuses after DOM reconciliation and isolates its background only while open. Large primary windows use `aria-hidden` and a focus guard, rather than the costly native `inert` traversal of thousands of controls; the overlay blocks pointer access. Other background layers use `inert`. Attribute observers keep the owners' current intent through retained-layer transitions, and close restores that intent before destination focus is restored. Its combobox keeps focus while arrows or Tab move the active option; search-type buttons are a separate group outside the listbox. Field highlights do not change the fuzzy scorer's text or group-first ordering.

**History is the back stack (`back.js`).** Only `back.js` writes history. Each route (`/s/12`) and each layer over it (a sheet, the drawer, the launcher, the Files tile or Browser panel where they cover the screen, a file over the tile's tree) is an entry, and each entry says how many layers it stands for and how many steps back the session list's entry is. The app's state is the truth and history follows it a moment later: opening a layer pushes an entry, closing one with a tap goes back past it, and a new route first goes back past the layers above the current one. Back that the person makes closes the layers above the entry it lands on; back to another route reaches `store.js` through `onRoute`. Traversals `back.js` makes itself reach no one. So:

- Navigate with `navigate()` (which calls `pushRoute`); do not call `history.pushState` or `history.back()` elsewhere. To drop a query from the address, use `replaceAddress`, which keeps the entry's marks.
- Something new that covers the screen, or that back should close, is a layer: `useBack(open, close)` in the component that shows it, where `close` makes `open` false. Sheets get theirs from `sheets.js`, one per sheet opened from another (the menu, then the model picker).
- On phones the window clips sideways: the conversation sliding in from the right (a route, a swipe's lean) would make the page wider than the screen, and a phone's browser widen and pan its view to fit.
- A finger's or a mouse's press and click within 280 ms of a layer opening or closing, or a route opening, at a tap (a pointer let go in the 400 ms before) is let go, focus and all: a quick second tap would land on whatever slid in under it (a tile of the sheet that rose, the scrim that closes it). What moves on its own (a reply opening a session, the server closing a sheet, Escape) holds nothing back, and keys and scripts never are.
- New entries wait for the page's first tap or key, since Chrome's back button skips entries a page adds before anyone touches it: the list's entry under a conversation opened straight away on a narrow screen, and the entries of layers already open at load (the chat a notification opened, a panel the tab kept).

**Pia chat (`pip.js`, `pip-attachments.js`).** The panel's uploads, submits, image thumbnails, and Markdown image paths use its own conversation ID, never the session behind it. The browser-only attachment draft outlives panel mounts, scopes itself to account and Pia ID, and holds upload identities and submit tokens so late callbacks cannot restore removed files or clear newer drafts. Unknown authentication or conversation IDs during reconnect are not a scope change. Files survive closing and reopening the panel, not a page reload; text keeps its existing local-storage draft. The normal upload and submit endpoints retain their size, file-access, and image-capability checks; Pia does not choose another model for an attachment. Opening the pending-memory sheet uses the private Pia ID even on Home. Panel cleanup restores focus only if it is still in the outgoing panel or on the body, not when a destination sheet already took it.

**Pia resize (`pip-window.js`).** Resize uses pointer capture on the same edge/corner zones for mouse and touch, at widths of 768px and above. The preferred size is local to the account/browser; CSS clamps it to the viewport without overwriting it.

**Extensions hub (`sheets/gallery.js`).** For owners with the gallery on, Extensions and the gallery share Discover, Installed, and Updates. The hub keeps one listing for its cards and embedded detail; `ExtensionsContent` supplies built-in and local module controls. Its list and entry sheet routes retain the same component so phone Back preserves search. Trail keys do not depend on whether the gallery is enabled: turning it off falls back to standalone management without adding another Back step. Source and update reviews stay separate sheets; updates still bind approval to the displayed pin and enabled state.

**Extensions' browser modules (`extension-ui.js`).** `hello` lists the browser modules a person's tabs load (`server.ui`: each module's name, title, and address, with its version in it). The tab imports each, and imports it again when its address changes: the server sends `hello` again when a browser module comes, goes, changes who it is for, or one of the files it serves changes (`ExtensionWebs` watches its folders), and when its module's new version installs other tools. A reload that leaves all that as it was leaves the address as it was, so tabs keep the browser module they loaded (they may hear `hello` again for other reasons). Event streams and poll queues cut off a tab more than 8 MB behind that took nothing for 30 s, or any tab 128 MB behind (`http/events.ts`); it connects again and gets a full view. A large first view is no reason: the tab has had no time to take it. A polling tab with an answer on its way is taking it until it polls again (one that never does ends 60 s after its last poll or answer), and a stream's ping checks too, so a stalled tab is cut off with no new events for it. A browser module is meant to add only through `pocket` (it runs in the page, so nothing stops it from more), and one that throws is caught there: its notice, its row in the Extensions sheet, its page's error box. One that failed stays listed (`dead`) but adds nothing more, until its module installs other tools: then the tab loads it again, as it may have failed on a tool the server did not have yet. Its events come as `ext` (`{ module, event, data }`). How a module's tools' calls show (`pocket.toolCall`) reaches `calls.js` and `turns.js` through setters, as they import nothing. Each `ui` entry lists the tools its module installs (from the loader), and a module describes only those; what a describer gives is used only when it is text. When a module goes, `sheets.js` takes its sheets out of the ones back would bring back (`onExtensionsGone`). A tab in safe mode (`?noext=1`, kept as `pocket.noext` in session storage) loads none of them.

**Contracts with the server.**

- Event names and shapes (`hello`, `view`, `chat`, `peek`, `subagents`, `ext`, …) and the sheet types the server names (`sheet: "chat"`).
- The `pocket.*` keys in local and session storage.
- Extensions' API: `web` on the server and `pocket` in the browser, at `POCKET_API`. Modules outside this repository depend on them: add to them freely, and change what they do only with a new version.
- `ATTACHMENTS_HEADING` and `splitAttachments` (which also reads the form sent before 0.14.0), which `ui.js` repeats from `entry-format.ts`.

## Updates of Pia itself

`Updates` (`updates.ts`, `app.updates`) works out `installKind` from where the server's files are: a git checkout (`git`), the global package folder of the Node.js that runs it, as `npm root -g` gives it (`npm-global`), another `node_modules` folder (`npm-local`), the npx cache (`npx`), or none of these (`unknown`; `npm-install.ts` does the npm kinds). Every kind shares one status (`UpdateStatus`), one set of checks (the launcher runs the server, no sessions busy, the warning tick), the two settings of the `updates` extension, and the outcome format in `update-state.ts`. What differs is where the newest version comes from and how it goes in:

- **The newest version.** An npm kind reads the registry's `latest` tag, and takes the notes, link, and date from the GitHub release of that version; if GitHub does not answer, the version stands without notes and is treated as one with a warning. A git checkout reads GitHub's newest release, or the version tags.
- **Git.** The release's commit is fetched under `refs/pocket-update/target`, packages install in `.pocket-update/staging/`, and the branch moves forward.
- **Global npm.** Only when the server's user can write the package and its parent folder, and the launcher advertises `PI_POCKET_NPM_ROLLBACK=1`. The new version installs through `npm-update.ts` in a separate global prefix under the sibling `.pi-pocket-update/staging/`. `update-state.ts` swaps the whole package, keeping the old one in `previous/`. The sibling folder also holds `pending.json` and `last.json`, so replacing the package does not replace recovery state. Before each server spawn, the launcher repairs a missing live folder from the pending update's copies; the server also checks before loading app modules. The launcher swaps the kept copy back when the server does not start; this needs no network. A successful start removes `previous/`. An older launcher requires a full quit and start before npm updates become available.
- **Local npm and npx.** Nothing in the app can change these. Their status has a blocker with the command to run (`npm install pi-pocket@latest`, or `npx pi-pocket@latest`).

A release with a warning (or notes that could not be read) is never installed by itself and is not rolled back by itself, whatever the kind. The browser module (`extensions/updates/index.js`) only shows `installKind` in words and the blockers the server gives: it holds no rule of its own.

## Checking a change

- **Every change:** `npm run check` (types, and no unused imports or locals in the TypeScript), `npm run lint`, and `npm test`.
- **Server:** the tests drive a real `PocketApp` with a scripted model, a restart included (`openApp` on the same folder). The built-in browser and peek tiles also run in a real Chromium where one is installed.
- **Web:**
    - `node --check` each file you edit.
    - Then open the app and use what you changed, with the console open.
    - A change that moves code between modules is a move only when the moved code is the same and the loading order above is kept.

## Native codemode

`extensions/codemode.ts` uses `pi-durable/codemode`; there is no second executor. On and Only change declarations, not execution or the store. A small sandbox adapter observes native discovery results and stores reference names in `pocket.codemode-references` before delivery. A tool API adapter records read-note IDs and validated write paths. Native tasks still own validation, guards, replay, cancellation, output budgets, and structured results. Result details carry the compact metadata into history, including on Stop. `compacted-references.ts` scans fork-aware raw history to the latest reset. Memory resolves note IDs again; codemode resolves tool names again. Neither reference grants access.

Only filters request declarations. Durable 1.5 classifies calls against the stored request before that filter, so a `beforeTool` check also rejects hidden direct calls. Stored calls are not rewritten. Browser and Ink Board image reads are model-only UI exceptions. Native nested guard approvals attach to the parent card but keep their unique nested call IDs. `projection.ts` projects native nested progress into that card's existing call list.

On first native use, `pocket.codemode-transition` copies legacy `pocket.codemode-store` values into `pi.codemode.store` once. Existing native values win on a key conflict; the old document is left intact. The native store is rewindable and forks as of the fork point. The legacy document's latest/current semantics are unchanged. On/Only switches share the native store and never repeat the copy. This transition is not a dependency rollback; restore the complete pre-upgrade backup to return to 1.4.

### Retention hook API boundary

Before-request hooks use `host.history(id).agent(context)` and `.context(context)`, backed by the native Conversation readers. They do not cast HookApi to ToolExecutionApi or silently use an empty tool list when a method is absent. The tool-name filter uses the current native callable registrations. The note filter uses the current native cwd, then approved-note and project-scope checks. Tests inspect actual post-compaction requests for pre-discovery, pre-read, post-read, and reset branches. A minimal HookApi without agent/context methods exercises both injection hooks.
